## 2. Proposed Multi-Photo Widget Layout

Replace the current single-purpose `Coin Image` panel with a compact `Photos` panel in the same left-column area.

Recommended layout:

```text
Photos
--------------------------------------------------
[primary preview image or empty-state text]

[Add Photos] [Remove] [Set Primary]
[Move Up]    [Move Down]

Attached Photos
--------------------------------------------------
Primary | Role          | File
*       | FRONT         | 1920_1c_front.jpg
        | BACK          | 1920_1c_back.jpg
        | CERT_LABEL    | slab_label.jpg

Selected Photo
--------------------------------------------------
Role:  [editable role combobox]
Notes: [short entry]
```

Design choices:

- Keep the panel in the current left-column image area to avoid a broader GUI redesign.
- Keep the main preview large enough to support collector confidence.
- Use a small `ttk.Treeview` or `Listbox` for attached photos.
- Use role labels from `PhotoRole`.
- Do not add a new top-level window for entry; keep the collector in the existing add-item flow.
- Do not add drag-and-drop in Phase 1C. Up/down buttons are simpler and testable.

Empty state:

```text
No photos selected
```

This should be shown in the preview and attached-photo list before selection.

## 3. Photo-Role Editing Flow

Role editing should be immediate but reversible before saving.

Recommended flow:

1. Collector clicks `Add Photos`.
2. App opens a multi-file picker.
3. App creates one `ItemPhoto` per selected file.
4. First new photo becomes primary if there is no existing primary.
5. Role defaults are assigned conservatively:
   - first photo: `FRONT`
   - second photo: `BACK`
   - remaining photos: `OTHER`
6. Collector selects a photo in the attached-photo list.
7. Collector changes role from an editable role combobox.
8. Collector may type notes for the selected photo.
9. The in-memory `current_item_photos` list is updated.
10. Saving the item persists `photos` through `CoinItem`.

Supported role values:

- `FRONT`
- `BACK`
- `HOLDER_FRONT`
- `HOLDER_BACK`
- `EDGE`
- `DETAIL`
- `CERT_LABEL`
- `OTHER`

Manual role text:

- The role combobox may be editable, but implementation should normalize through `PhotoRole.normalize`.
- Unknown role text becomes `OTHER`.
- Do not reject saving because of unusual role text.

## 4. Primary-Image Behavior

The primary image remains the one image used by existing single-image behavior.

Rules:

- Exactly one attached photo is effective primary when photos exist.
- `Set Primary` marks the selected photo primary and unmarks all others.
- The primary photo should appear with a visible marker in the attached-photo list, such as `*`.
- The main preview should display the selected photo, not necessarily always the primary photo.
- The primary photo should be easy to identify while browsing other attached photos.
- On save, `CoinItem.sync_image_path_from_primary()` or equivalent backend behavior ensures `image_path` reflects the primary photo.
- The collection table remains unchanged and continues to show ID, country, denomination, year, and grade.
- Any existing display that expects one image should use `item.primary_image_path` or `item.image_path`.

Default behavior:

- If photos are added to an empty form, the first photo becomes primary.
- If the primary photo is removed and other photos remain, the first remaining photo becomes primary.
- If a legacy item has only `image_path`, editing/viewing should show that synthesized photo as primary through `normalized_photos()`.

## 5. Add, Remove, and Reorder Behavior

### Add Photos

Use:

```python
filedialog.askopenfilenames(...)
```

Supported extensions should match the backend-supported local image extensions where practical:

- `.jpg`
- `.jpeg`
- `.png`
- `.webp`
- `.bmp`
- `.tif`
- `.tiff`

Behavior:

- Manual cancellation makes no state change.
- Duplicate selected paths should be ignored or warned once.
- Paths are stored exactly as selected; do not copy, move, rename, or delete files.
- Existing `CoinCollectionApp.upload_image` may remain for one-image compatibility, but Phase 1C should avoid requiring it as the only image state.

### Remove Photo

Behavior:

- Removes the selected `ItemPhoto` from in-memory form state.
- Does not delete the file from disk.
- If removed photo was primary, first remaining photo becomes primary.
- If no photos remain, preview returns to empty state.

### Reorder Photos

Behavior:

- `Move Up` and `Move Down` reorder `current_item_photos`.
- Reordering updates `display_order`.
- Reordering does not change primary unless the collector explicitly clicks `Set Primary`.
- Serialization remains deterministic through Phase 1B helpers.

### Relabel Photos

Behavior:

- Changing the role updates selected `ItemPhoto.role`.
- Changing notes updates selected `ItemPhoto.notes`.
- Role and notes are local until save.

## 7. Banknote Terminology Handling

Backend roles remain neutral:

- `FRONT`
- `BACK`
- `HOLDER_FRONT`
- `HOLDER_BACK`
- `EDGE`
- `DETAIL`
- `CERT_LABEL`
- `OTHER`

Display labels may be collector-friendly:

- `FRONT`: "Front / Obverse"
- `BACK`: "Back / Reverse"
- `HOLDER_FRONT`: "Holder Front"
- `HOLDER_BACK`: "Holder Back"
- `CERT_LABEL`: "Certification Label"

Reason:

- Coins can use obverse/reverse language.
- Banknotes can use front/back language.
- The same backend role model works for tokens, medals, slabs, banknotes, and unusual collectibles.

Avoid:

- Storing coin-only role names in the GUI.
- Requiring a collectible type field before photos can be attached.

## 8. Error and Empty-State Behavior

### Empty Photo State

- Show `No photos selected`.
- Disable `Remove`, `Set Primary`, `Move Up`, and `Move Down`.
- Save should remain blocked only if current product behavior still requires at least one photo.
- If Phase 1C wants to allow no-photo collection entries, that should be a separate approval because it changes current save behavior.

### Missing Image File

- Keep photo metadata visible.
- Show `Image file not found` in preview.
- Do not remove the photo from the item.
- Do not block opening details or editing.

### Unsupported Image Format

- Picker filters supported image files.
- If legacy data has unsupported extension, show it in list and preview failure text.
- Let Photo Vault continue auditing invalid extension.

### Duplicate Selected Files

- Detect duplicates by normalized path in current form state.
- Do not add duplicates silently.
- Show a concise warning with count skipped.

### Inaccessible OneDrive Path

- Treat as preview failure.
- Preserve path metadata.
- Do not delete or rewrite path.

### Multiple Primary Photos from Legacy/Malformed Data

- `CoinItem.normalized_photos()` already normalizes deterministically.
- GUI should display the normalized primary state.
- Saving through GUI should write a single primary photo.

### Manual Cancellation

- File picker cancellation should leave current photo state unchanged.

## 9. Backward-Compatible Edit Flow

Recommended Phase 1C approach:

- Do not try to bolt multi-photo editing onto repeated `simpledialog` prompts.
- Replace `edit_item` with a small edit dialog only if implementation remains scoped.
- The edit dialog should load:
  - country
  - denomination
  - year
  - grade
  - notes
  - `item.normalized_photos()`
- Existing text save behavior remains unchanged.
- Photo changes save through `CoinItem.photos`.
- `image_path` remains primary alias through backend serialization.

Conservative alternative:

- Phase 1C may implement multi-photo add flow and details gallery first.
- Editing existing item photos can be split into Phase 1C.2 if needed.

Recommendation:

- Include existing-item photo editing only if it can reuse the same photo-list component from the add-entry form.
- Avoid separate divergent photo-edit widgets.

## 12. Regression Risks

Risk level: medium.

Primary risks:

- Current detection flow depends on `self.app.current_image_path`.
- Current save flow requires one uploaded image.
- Replacing one-image state with multi-photo state can accidentally break detector and advanced ID.
- Reusing a single `self.current_photo` reference may break previews if multiple thumbnails are introduced.
- `simpledialog` edit flow does not naturally support multi-photo editing.
- Item details currently use a simple messagebox; a new details window is a larger GUI surface.
- Tk image references must be retained to avoid blank previews.
- Tests should avoid fragile full Tk window automation where possible.

Mitigation:

- Keep detector using the primary or selected photo path only.
- Keep `self.app.current_image_path` synchronized to the primary photo for compatibility.
- Build photo-state helper methods that can be unit tested without real windows.
- Keep the collection table unchanged.
- Do not change backend model or migration in Phase 1C.
- Keep file operations metadata-only.
