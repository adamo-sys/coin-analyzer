## 2. Create New Interaction Flow

Recommended flow:

1. Collector opens `Collector Home -> Photo Inbox...`.
2. Collector clicks `Refresh Inbox`.
3. Photo Inbox displays pending Photo Sets.
4. Collector selects a Photo Set.
5. Collector clicks `Create New`.
6. Coin Analyzer loads the selected Photo Set photos into the existing main collection-entry form.
7. Coin Analyzer closes or leaves the inbox window open with a clear status.
8. Collector reviews/edit roles, primary image, country, denomination, year, grade, and notes.
9. Collector clicks existing `Save to Collection`.
10. Only after save succeeds, Coin Analyzer marks the source Photo Set as `ATTACHED`.
11. Inbox state is saved and refreshed.

The collector should not have to browse for files in this workflow.

## 3. Populating Existing Entry-Form Photo State

Implementation should reuse the Phase 1C entry form photo state instead of creating a separate creation flow.

Recommended helper:

```python
def item_photos_from_inbox_photo_set(self, manager, photo_set_id):
    paths = [photo.path for photo in manager.get_photo_set_photos(photo_set_id)]
    photos, skipped = self.add_photo_paths_to_list([], paths)
    return photos, skipped
```

Recommended load behavior:

- Clear current entry-form photo state before loading the Photo Set.
- Do not clear typed text fields unless explicitly decided during implementation review.
- Set:
  - `self.current_item_photos`
  - `self.selected_photo_index`
  - `self.app.current_image_path`
- Refresh:
  - `self.refresh_photo_list()`
  - `self.display_selected_photo()`

Open design question for approval:

- Should loading a Photo Set clear existing country/denomination/year/grade/notes?

Recommendation:

- If the entry form already contains text or photos, ask for confirmation before replacing the current form state.
- For Phase 2B.2, keep this simple: if the form is non-empty, show a confirmation dialog.

## 4. Default Role-Assignment Strategy

Use existing Phase 1C behavior:

- First photo: `FRONT`
- Second photo: `BACK`
- Remaining photos: `OTHER`

Reason:

- This behavior is already tested.
- It works for coins and banknotes.
- It remains editable before save.
- It avoids adding new inference rules in Phase 2B.2.

Do not infer roles from filenames yet.

Filename-based role suggestions can be considered later if evidence shows it removes meaningful drag without surprising the collector.

## 5. Primary-Image Strategy

Use existing Phase 1C normalization:

- First loaded photo becomes primary if no primary exists.
- Exactly one effective primary is maintained.
- The collector may change primary before save.
- `image_path` remains synchronized to the effective primary.

Recommended behavior:

- Preserve Photo Set order from `PhotoInboxManager.get_photo_set_photos(photo_set_id)`.
- Assign primary to the first photo in that deterministic order.
- Do not mark a Photo Set attached merely because a primary was selected.

## 6. Save-Success Behavior

The key rule:

- Opening the entry form from a Photo Set must not complete inbox processing.
- Successful save completes inbox processing.

Recommended state handoff:

1. `Create New` stores pending inbox context on the GUI instance:
   - `self.pending_inbox_manager`
   - `self.pending_inbox_photo_set_id`
   - optionally `self.pending_inbox_dialog_refresh`
2. Existing `save_to_collection` saves the collectible.
3. If save succeeds and pending inbox context exists:
   - mark the Photo Set `ATTACHED`
   - pass the new item id if safely available
   - clear pending inbox context
   - refresh the inbox window if it is still open

Backend consideration:

- `CoinCollectionApp.add_to_collection(...)` currently returns `bool`.
- If implementation needs the new item id to call `mark_attached(photo_set_id, item_id=...)`, options are:
  - read the last-added item from `self.app.collection.get_all_items()` after success, or
  - add a narrow app-layer helper that returns the created item id.

Recommendation:

- Avoid changing `CoinItem` or collection persistence.
- Prefer a minimal app-layer return-id helper only if reading the saved item is too brittle.

## 7. Cancel and Failure Behavior

Cancel cases:

- Collector closes the Photo Inbox window after loading photos.
- Collector clicks `Clear Form`.
- Collector closes the app.
- Collector abandons entry without saving.

Required behavior:

- Photo Set remains `NEW` or whatever pending state it had before `Create New`.
- No inbox state transition occurs.
- No photo files are moved, copied, renamed, archived, or deleted.

Failure cases:

- Save validation fails because country or denomination is missing.
- Save fails in backend.
- Collection persistence fails.
- Photo Set has missing files.
- Photo Set was ignored/deferred from another open inbox window.

Required behavior:

- Do not mark `ATTACHED`.
- Preserve form state when possible.
- Show a clear error if the pending Photo Set can no longer be updated after save.
- Missing files should remain visible as references; they should not block opening the form unless the existing save behavior requires a primary image.

## 8. Inbox State Transition Rules

Allowed Phase 2B.2 transition:

```text
NEW / DEFERRED / ERROR
-> user clicks Create New
-> entry form loaded
-> user saves collectible successfully
-> ATTACHED
```

Do not transition on:

- selecting a set
- opening the inbox
- clicking Create New
- loading the form
- editing photo roles
- editing text fields
- running detection
- clearing or cancelling the form

If the user starts from `DEFERRED`, successful save may still mark `ATTACHED`.

If the set is `IGNORED`, `ATTACHED`, or `IMPORTED`, it should not appear in pending rows and should not be creatable.

## 9. Refresh Behavior

Recommended behavior after `Create New`:

- Do not immediately refresh the inbox in a way that hides the selected set before save.
- The set is still pending until save succeeds.

Recommended behavior after successful save:

- Call `mark_attached`.
- Refresh pending inbox rows.
- Selected set disappears from pending list because `ATTACHED` is terminal.
- Main collection list refreshes as it already does after save.

Recommended behavior after save failure:

- Do not refresh away the pending set.
- Keep the pending context active.

## 12. Regression Risks

Primary risks:

- Marking a Photo Set `ATTACHED` before the collectible actually exists.
- Clearing a collector's partially typed entry form unexpectedly.
- Losing selected Photo Set context after loading the form.
- Saving a collectible but failing to mark the Photo Set attached.
- Marking the wrong Photo Set attached if multiple inbox windows are open.
- Breaking existing manual photo attachment.
- Accidentally implementing Phase 2B.3 attach-to-existing behavior.
- Accidentally moving files or treating inbox as photo ownership.

Mitigations:

- Keep pending inbox context explicit and small.
- Transition inbox state only after save success.
- Add tests for failed save and cancel.
- Keep Create New path using existing `current_item_photos` state.
- Leave Attach to Existing disabled.
- Keep file references in place.
