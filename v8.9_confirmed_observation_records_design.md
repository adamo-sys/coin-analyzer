# v8.9 Confirmed Observation Records Design

## Status

Design only. No production engine, threshold, model, recommendation, or collection-schema change is authorized by this document.

## Mission

Preserve explicit collector outcomes as durable local evidence for future offline evaluation. Coin Analyzer records what the collector confirmed; it does not modify its own behavior from that record.

```text
Collector action
-> ConfirmedObservationStore
-> Durable local evidence
-> Future offline evaluation (separately approved)
```

## Current Context

`coin_collection_gui.py` currently appends detection attempts to `data/debug_feedback.csv` and later tries to update the final matching row when the collector saves an item. That CSV is a debugging artifact, not a reliable learning dataset: it has no schema version, immutable record identifier, outcome taxonomy, engine version, evidence snapshot, or durable association to one collector decision.

The existing `atomic_json.py` helper provides same-directory temporary-file writing, `fsync`, and `os.replace` for complete JSON documents. Backup packages already verify archive integrity, manifests, and checksums.

`data/debug_feedback.csv` remains unchanged. It is not migrated, read, or used by this milestone.

## Ownership and Public API

Create a dedicated `ConfirmedObservationStore`. It owns schema validation, normalization, serialization, persistence, duplicate protection, and tolerant loading. GUI callbacks only construct an observation from already available facts and call the store after the relevant collector action succeeds.

```python
class ConfirmedObservationStore:
    def __init__(self, path: str = DEFAULT_CONFIRMED_OBSERVATIONS_PATH) -> None: ...
    def append(self, observation: ConfirmedObservationRecord) -> AppendResult: ...
    def load(self) -> ObservationLoadResult: ...
    def contains(self, observation_id: str) -> bool: ...
```

`append()` returns a structured result. It never silently drops a failed write. It is idempotent by `observation_id`: a repeated call returns an already-recorded result and does not create a second record.

The store is not an engine dependency. No production engine imports it or reads its contents in this phase.

## DTOs and Enums

All DTOs are immutable where practical and expose deterministic `to_dict()` methods.

```text
ObservationOutcome
  ACCEPTED
  CORRECTED
  DEFERRED
  REJECTED

FeedbackCategory
  OCR_MISREAD
  IDENTIFICATION_MISMATCH
  IMAGE_READINESS_FALSE_POSITIVE
  IMAGE_READINESS_FALSE_NEGATIVE
  REFERENCE_DATA_CONFLICT
  COLLECTION_DUPLICATE_MISS
  COLLECTION_WORKFLOW_FRICTION
  OTHER
```

`ConfirmedObservationRecord` fields:

```text
schema_version          required string, initially "1"
observation_id          required immutable UUID/string
created_at              required ISO-8601 UTC timestamp
outcome                 required ObservationOutcome
category                required FeedbackCategory
suggested_values        normalized JSON object supplied by the originating flow
confirmed_values        normalized JSON object; empty only for DEFERRED/REJECTED
engine_name             required string
engine_version          required string; "unknown" is explicit, never inferred
recognition_method      required string
application_version     required release string supplied by the application
photo_references        ordered, normalized path/reference strings only
evidence_snapshot       JSON-safe snapshot of displayed evidence/reasons
source_workflow         required stable workflow identifier
collector_note          optional free text
```

The record stores references and evidence metadata only. It never copies image files, collection data, credentials, or unrelated Photo Vault state.

## Outcome Trigger Semantics

| Outcome | Trigger | Required confirmation |
| --- | --- | --- |
| `ACCEPTED` | A detection-backed prediction matches the collector's saved values. | `add_to_collection()` completed successfully. |
| `CORRECTED` | A detection-backed prediction differs from the collector's saved values. | `add_to_collection()` completed successfully. |
| `DEFERRED` | Collector deliberately selects a future `Defer Result` action. | The explicit deferred observation was written successfully. |
| `REJECTED` | Collector deliberately selects a future `Reject Result` action. | The explicit rejected observation was written successfully. |

Cancel, window close, validation failure, and collection persistence failure write no observation. Photo Inbox `Defer` and `Ignore` are not observation outcomes; they remain Photo Inbox states with their current meaning.

The initial implementation integrates only `ACCEPTED` and `CORRECTED` after a successful collection save. `DEFERRED` and `REJECTED` require separately approved explicit controls; this milestone must not infer either outcome.

## Persistence Decision

Use a **versioned atomic JSON document**, not JSON Lines.

```json
{
  "schema_version": "1",
  "records": [
    { "observation_id": "...", "outcome": "CORRECTED" }
  ]
}
```

The store rewrites the small document using `atomic_json.write_json_atomically`. The records themselves are immutable in meaning: existing IDs are never edited, and an existing ID prevents a duplicate append.

Rationale:

- The existing helper already provides Windows-friendly temporary-file, `fsync`, and `os.replace` semantics.
- A crash before replacement preserves the prior valid document; a crash after replacement leaves a complete new document.
- Tolerant loading can salvage valid records from a malformed `records` list and report skipped entries without stopping the app.
- Deterministic complete-document serialization is straightforward to test and export later.
- Backup packages can include one identified file and verify it by checksum.

JSON Lines would make one-record append cheap, but would require an additional durable append protocol, partial-final-line repair rules, and more complicated cross-platform failure handling. It provides no benefit at this early collector-confirmed volume.

Recommended default path:

```text
collection_data/app_state/confirmed_observations.json
```

The path is constructor-injected in all tests and must never default to a live repository data file in a test.

## Validation, Idempotency, and Recovery

- Validate document and records before writing; reject invalid new observations with a structured error.
- Sort serialized records by `created_at`, then `observation_id`, while keeping `photo_references` in collector/source order.
- Treat an existing `observation_id` with identical content as idempotent.
- Treat an existing identifier with different content as a structured conflict; never overwrite it.
- On load, keep valid records, list malformed-record warnings, and never mutate or silently repair the source file.
- If the root document cannot be read, return an empty result plus a structured error; do not replace or truncate it automatically.
- Temporary-file cleanup relies on the existing atomic helper and must be tested through genuine write/replace failure simulation.

## GUI Integration Points

The only initial GUI seam is the successful branch of `CoinCollectionGUI.save_to_collection()` in `coin_collection_gui.py`.

1. Preserve the current successful collection-save behavior.
2. Compare the successful saved values with the existing successful detection suggestion.
3. Construct `ACCEPTED` or `CORRECTED` data using the existing detection result, form values, current ordered photos, and displayed method/confidence evidence.
4. Call `ConfirmedObservationStore.append()`.
5. If the observation write fails, show a non-deceptive warning that the item was saved but its feedback record was not; do not roll back the successfully saved collection item.

No new dialog, dashboard, automatic correction, or engine invocation is part of this milestone. Explicit defer/reject controls are deferred.

## Application Version

The repository currently has inconsistent version literals in historical code and documentation. The milestone must not use `README.md` or `backup_manager.APP_VERSION` as a runtime source. Add one narrowly scoped, release-maintained application metadata constant only if needed to provide the required `application_version` field. Its ownership is release metadata, not the observation store or GUI.

## Backup and Privacy

- `BackupManager.create_backup_package()` includes the confirmed-observations document when present.
- The manifest records the file normally; checksum verification and existing restore allow-list behavior cover it under `collection_data/app_state/`.
- No automatic backup is created solely because an observation is appended.
- Records remain local. No network, cloud sync, telemetry, scraping, or external API use is permitted.
- Retention is collector-controlled through ordinary backup/restore management; this milestone adds no delete, edit, or export UI.

## Test Plan

Add focused tests using temporary directories and injected clocks/IDs where needed:

1. DTO validation, Unicode, and deterministic serialization.
2. `ACCEPTED` and `CORRECTED` records with evidence and ordered photo references.
3. Duplicate append is idempotent; conflicting same-ID append fails.
4. Atomic successful write and replacement of an existing document.
5. Serialization, write, and replace failures preserve the previous document and clean temporary files.
6. Malformed root and malformed individual records degrade without app crashes.
7. Store paths are injected and never touch `data/collection.json`.
8. A successful detection-backed collection save records exactly one outcome.
9. Cancel, validation failure, and collection save failure record nothing.
10. No engine imports or reads the store.
11. Backup package includes and verifies the record document when present.
12. Existing GUI, collection, backup, and full discovery suites remain green.

## Explicit Stop Line

This milestone does not:

- read feedback from production engines;
- tune thresholds, weights, or models;
- cluster failures or generate proposals;
- compare engine versions;
- alter collection or photo persistence schemas;
- migrate `data/debug_feedback.csv`;
- add `DEFERRED`/`REJECTED` UI controls;
- add analytics, dashboards, exports, networking, cloud sync, or external APIs.

Future evaluation, comparison, and proposal work requires a separate approved design after enough explicit collector-confirmed records exist.
