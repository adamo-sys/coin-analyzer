# v8.8 Phase 4C Design: Reference Aggregation And Conflict Reporting

Status: Design only
Implementation: Not started
Baseline: Phase 4B complete at `06605de` with 1,472 tests passing

## Mission

Aggregate multiple `ReferenceProvider` instances deterministically while preserving every source claim and making disagreements visible. Phase 4C must not silently select a winner or infer an identification.

Product principle:

```text
Preserve claims.
Expose conflicts.
Do not silently overwrite.
```

## Current State

Phase 4A supplies neutral issue, source, provenance, validation, and provider-contract DTOs. Phase 4B proves those contracts with `LocalJsonReferenceProvider` and `ManualReferenceProvider` using safe local data.

No current component:

- registers more than one provider
- combines provider queries
- groups records from separate providers
- detects field disagreements across sources
- assigns source priority or resolves a conflict

Phase 4C creates that aggregation layer only. It is a library layer and does not change either concrete provider's ownership or persistence behavior.

## 1. Public API

Recommended public type:

```python
class ReferenceProviderAggregator:
    def __init__(self, providers: Iterable[ReferenceProvider] = ()):
        ...

    def register(self, provider: ReferenceProvider) -> None:
        ...

    def providers(self) -> Tuple[ReferenceProvider, ...]:
        ...

    def provider_ids(self) -> Tuple[str, ...]:
        ...

    def get_issue(self, issue_id: str) -> AggregatedReferenceResult:
        ...

    def search(self, query: ReferenceQuery) -> AggregatedReferenceResult:
        ...

    def list_issues(
        self,
        filters: Optional[ReferenceFilters] = None,
    ) -> AggregatedReferenceResult:
        ...

    def validate(self) -> AggregateValidationReport:
        ...
```

`ReferenceProviderAggregator` deliberately does not implement `ReferenceProvider`. Its result is a multi-source report, not a single-provider `ReferenceSearchResult` and not a synthesized `ReferenceRecord`.

`register(...)` accepts only runtime-conformant providers. It rejects duplicate non-empty provider IDs with `ValueError`; registration never replaces an existing provider implicitly. No global registry, discovery, persistence, or network behavior is allowed.

Recommended aggregate DTOs:

```python
@dataclass(frozen=True)
class ReferenceClaim:
    provider_id: str
    source: ReferenceSource
    source_record_id: str
    issue_id: str
    field_name: str
    raw_value: str
    normalized_value: str
    source_ref: Optional[SourceRef] = None

@dataclass(frozen=True)
class ReferenceIssueGroup:
    issue_key: str
    records: Tuple[ReferenceRecord, ...]
    claims: Tuple[ReferenceClaim, ...]
    conflicts: Tuple[ReferenceConflict, ...]

@dataclass(frozen=True)
class ReferenceConflict:
    issue_key: str
    field_name: str
    conflict_type: ReferenceConflictType
    claims: Tuple[ReferenceClaim, ...]
    notes: str = ""

@dataclass(frozen=True)
class AggregatedReferenceResult:
    groups: Tuple[ReferenceIssueGroup, ...]
    provider_errors: Tuple[ReferenceProviderError, ...]
    warnings: Tuple[str, ...] = ()

@dataclass(frozen=True)
class AggregateValidationReport:
    provider_reports: Tuple[ReferenceValidationReport, ...]
    provider_errors: Tuple[ReferenceProviderError, ...]
    findings: Tuple[ReferenceValidationFinding, ...]
```

All aggregate DTOs should expose deterministic `to_dict()` serialization. Their fields are read-only and they never modify underlying `ReferenceRecord`, `CanadianIssue`, `ReferenceSource`, or `SourceRef` instances.

## 2. Aggregation Ownership

The aggregator owns only:

- explicit provider registration and registration order
- isolated calls to registered providers
- record grouping by the safe identity rule below
- claim projection from returned records
- conflict detection and aggregate reporting
- deterministic ordering

It does not own:

- provider loading, file paths, or manual-record mutation
- collection data or collection persistence
- photo/OCR/image-assessment data
- candidate identification or match scoring
- GUI presentation
- conflict resolution, source ranking, or user override storage

Provider records remain authoritative only for the claims made by their own sources. An aggregate group is a view over claims, never a merged canonical Canadian issue.

## 3. Provider Ordering Model

The constructor's iterable order is the registration order. `register(...)` appends a provider after existing registrations.

Registration order controls only deterministic execution and display tie-breaking:

1. provider registration index
2. provider ID
3. source ID
4. `reference_sort_key(record)`
5. source record ID

It does not give factual precedence. A provider registered first cannot overwrite, suppress, or resolve a later provider's claim.

The aggregator should retain immutable registration entries internally so a query uses the same order throughout its execution. Calling `providers()` returns a tuple snapshot, not a mutable registry.

## 4. Issue Identity Matching Rules

Phase 4C uses one intentionally conservative cross-provider identity rule:

```text
issue_key = normalize_text(record.issue.issue_id)
```

Records enter the same `ReferenceIssueGroup` only when they have the same non-empty normalized `issue_id`. The aggregate result should keep the original raw issue IDs within the constituent records and claims.

Why this boundary matters:

- country, denomination, and year are not enough to identify a unique issue
- shared design markers may be incomplete or inconsistent
- similarity matching would be identification work
- grouping uncertain records would make a false conflict appear authoritative

Records with empty issue IDs remain separately visible as ungrouped validation-problem records, keyed deterministically by provider ID, source ID, and source record ID. They are never matched to another provider's records.

There is no fallback grouping by denomination, year, text search result, measurements, catalogue number, variety, or image evidence in Phase 4C. A later identification phase may propose candidates while retaining this aggregation layer's stricter identity model.

## 5. Source-Claim Grouping

For every `ReferenceRecord` in an identity group, the aggregator projects claims for these approved conflict-bearing fields:

- `date_text`
- `mintage`
- `weight`
- `diameter`
- `composition`
- `variety`
- `catalogue_numbers` by catalogue namespace

Each claim retains:

- provider ID
- full `ReferenceSource`
- record/source record ID
- raw field value
- deterministic normalized value
- matching `SourceRef` when the provider supplied one

If a field-level `SourceRef` exists for the field and source record, it supplies the raw and normalized representation. Otherwise, the aggregator creates a derived read-only `ReferenceClaim` from the `CanadianIssue` field and identifies it with the record's source metadata. It does not mutate the record to add a `SourceRef`.

For `catalogue_numbers`, each namespace is represented as a separate field name such as `catalogue_numbers.synthetic`. Different namespaces are separate facts and are never treated as a conflict simply because their identifiers differ.

All records and all claims remain in the result even when the values agree. Agreement means no conflict is reported; it does not discard provenance.

## 6. Conflict DTOs And Detection

The existing `ReferenceConflictType` enum is sufficient for the initial approved fields:

| Field | Conflict type | Normalization used |
| --- | --- | --- |
| `date_text` | `DATE_TEXT` | `normalize_date_text` |
| `mintage` | `OTHER` | `normalize_text` |
| `weight` | `WEIGHT` | raw normalized text, not a unit conversion |
| `diameter` | `DIAMETER` | raw normalized text, not a unit conversion |
| `composition` | `COMPOSITION` | `normalize_composition` |
| `variety` | `VARIETY` | `normalize_variety` |
| `catalogue_numbers.<namespace>` | `CATALOGUE_NUMBER` | `normalize_catalogue_id` |

A conflict exists when a single non-empty `issue_key` has two or more distinct non-empty normalized values for the same field. Empty or absent values remain visible as claims but do not create conflicts by themselves.

Conflict ordering:

1. issue key
2. field name
3. conflict type
4. claim provider registration order
5. claim source ID
6. claim source record ID

The conflict DTO contains every disagreeing claim. It has no `selected_value`, `winner`, `confidence`, or resolution-status field in Phase 4C. Those concepts require an explicitly approved policy and, for user decisions, future persistence/UI work.

## 7. User Override Behavior

No user override precedence is approved for Phase 4C.

`ManualReferenceProvider` records are normal attributable source claims. They participate in aggregation and conflict reports exactly like local JSON claims; they do not replace, hide, or outrank any other source.

A later phase may add an explicit collector override object with:

- a target issue key and field
- selected source claim or collector-entered value
- reason and timestamp
- explicit local persistence
- clear visual/audit distinction from source facts

That future design must decide precedence and reversal behavior. Phase 4C must not infer an override from `ReferenceSourceType.MANUAL`.

## 8. Provider Failure Isolation

Every provider call is isolated at the aggregator boundary.

For `search(...)` and `list_issues(...)`:

1. invoke each registered provider in registration order
2. retain successful records
3. append returned `ReferenceSearchResult.provider_errors`
4. catch ordinary provider exceptions and convert them to a deterministic `ReferenceProviderError`
5. continue with remaining providers
6. group only successfully returned records

Recommended aggregation error codes:

- `AGGREGATE_PROVIDER_SEARCH_FAILED`
- `AGGREGATE_PROVIDER_LIST_FAILED`
- `AGGREGATE_PROVIDER_LOOKUP_FAILED`
- `AGGREGATE_PROVIDER_VALIDATE_FAILED`
- `AGGREGATE_PROVIDER_RESULT_INVALID`

`get_issue(...)` follows the same isolation rules. An unavailable provider contributes a structured error but cannot prevent another provider's matching record from appearing.

No stack trace belongs in aggregate DTOs, export data, or future GUI text. The original exception may be logged through existing developer diagnostics only if the repository already has an appropriate local diagnostic pattern; Phase 4C does not introduce one.

## 9. Deterministic Ordering

The aggregator must return byte-for-byte equivalent DTO serialization for identical provider registrations, provider outputs, and query inputs.

- Providers run in registration order.
- Provider errors sort by registration order, code, then message.
- Records within a group sort by provider registration index, provider ID, source ID, `reference_sort_key`, then source record ID.
- Groups sort by issue key; ungrouped validation-problem records sort after normal groups using their deterministic surrogate key.
- Claims and conflicts follow the ordering rules above.
- Validation reports follow provider registration order.

The aggregator must not use set iteration, dictionary insertion order from a provider, timestamps, random IDs, filesystem order, or exception object representations as ordering inputs.

## 10. Aggregate Validation Flow

`validate()` performs no searches and no provider mutation.

For each registered provider:

1. call `provider.validate()` in registration order
2. retain the complete provider validation report
3. isolate exceptions as `AGGREGATE_PROVIDER_VALIDATE_FAILED`
4. collect reported duplicate issue IDs and source IDs without removing records

The aggregate report then adds aggregation-level findings for:

- duplicate registered provider IDs, prevented at registration time
- empty issue IDs encountered in aggregate inputs
- same issue key appearing across multiple providers
- detected field conflicts
- provider failures

Aggregate findings must be additive. Provider findings retain their original provider/source context and are not rewritten or collapsed into a generic warning.

`validate()` may call a provider's own `validate()` lazily, because provider validation is part of the existing contract. It must not call `search()` or `list_issues()` to discover data.

## 13. Regression Risks

| Risk | Mitigation |
| --- | --- |
| One provider silently replaces another | Aggregate groups retain all records and have no selected value. |
| Similar issues are falsely merged | Group only on explicitly shared normalized `issue_id`. |
| Manual data becomes an implicit override | Treat manual records as equal source claims. |
| Provider exception hides usable results | Isolate each provider call and return structured errors. |
| Nondeterministic output confuses exports/tests | Registration and result ordering are explicitly defined. |
| Phase 4C becomes identification | No fuzzy matching, ranking, or fallback issue matching. |
| Data is copied or altered during aggregation | Aggregator creates read-only projections only. |
| Licensed or external sources leak into fixtures | Use synthetic providers and records only. |

## 15. Recommended Implementation Sequence

1. Add immutable aggregate DTOs and deterministic serialization helpers.
2. Add `ReferenceProviderAggregator` registration with duplicate-ID rejection.
3. Add provider-call isolation and aggregate provider-error handling.
4. Implement conservative issue-ID grouping and stable ordering.
5. Project field claims without modifying provider records.
6. Implement the approved field-conflict detector.
7. Add aggregate validation/reporting.
8. Add focused synthetic-provider tests, including throwing providers.
9. Run the focused aggregation suite.
10. Run full unittest discovery.

Stop after Phase 4C. Candidate identification, reference-provider ingestion, GUI integration, OCR, grading, pricing, and override persistence require separate approval.
