# v8.7 Phase 1 Design: Faster Collection Entry

Design status: proposed for review only.

Implementation status: not started.

This document is design-only. It does not lock implementation details until reviewed and approved.

## 1. Root-Cause Analysis

Collector Journey Audit evidence points to two sources of entry friction when processing a newly acquired collectible:

1. The main entry form asks the collector to repeatedly type common values for country, denomination, year, and grade.
2. The collection item model and main entry workflow treat a collectible as having one primary image path, while real coins and banknotes often need several supporting images.

The first problem is entry speed. The collector already has enough collection data to suggest many repeated values, but the main form mostly uses plain text entries. Grade already uses an editable `ttk.Combobox`, which is the right interaction pattern and should be extended, not replaced with a closed list.

The second problem is data shape. The collection record currently has `image_path: str`, which is useful for existing list displays and legacy records but too narrow for front/back, slab, certification label, edge, and detail photos. Photo Vault already stores photo metadata, but it is currently app-state metadata and audit/index behavior rather than the canonical photo list for each collection item.

The mission for Phase 1 is to reduce the time required to process a newly acquired collectible while preserving manual control and backward compatibility.

## 3. Recommended Ownership Boundary

Collection item photo attachments should be item-owned.

Recommended boundary:

- `CoinItem.photos` is the source of truth for photos attached to an owned collection item.
- `CoinItem.image_path` remains as a compatibility alias for the current primary photo path.
- Photo Vault remains an index, audit, search, coverage, and supplemental metadata layer.
- Photo Vault may continue to store candidate, reference, auction, sold, and app-state photo records that are not owned by collection items.
- Collection-item photo coverage should eventually be derivable from `CoinItem.photos` plus any legacy or supplemental `PhotoRecord` entries.

This avoids splitting the canonical state for one collection item between `data/collection.json` and `collection_data/app_state/app_state.json`.

## 4. Public API Impact

Expected public API changes:

- `CoinItem` gains a structured `photos` list.
- `CoinItem.from_dict` becomes backward-compatible and schema-tolerant.
- `CoinItem.to_dict` emits deterministic `photos` data.
- `CoinItem.primary_image_path` or equivalent helper returns the primary photo path.
- `CoinItem.image_path` remains readable and writable during compatibility period.
- `CoinCollection.add_item` and `update_item` continue to accept existing fields.
- `CoinCollectionApp.add_to_collection` must accept either a single image path or a list of structured photos in the implementation phase.
- `CoinCollection.export_to_csv` should retain `image_path` and add a deterministic multi-photo representation only after the design is approved.

No recommendation categories, intelligence engines, OCR behavior, grading behavior, or external integrations should change.

## 5. DTO and Data-Model Design

Recommended conceptual DTO:

```text
ItemPhoto
    path: str
    role: str
    is_primary: bool
    notes: str
    display_order: int
```

Recommended collection item shape:

```text
CoinItem
    id
    image_path
    photos: List[ItemPhoto]
    country
    denomination
    year
    grade
    notes
    ...
```

Recommended helper behavior:

- `CoinItem.normalized_photos()`
  - Returns a cleaned, deterministic photo list.
  - Interprets legacy `image_path` as one primary photo if `photos` is absent or empty.
- `CoinItem.primary_photo()`
  - Returns the first `is_primary` photo after normalization.
  - If none is marked primary, returns the first photo by `display_order`.
- `CoinItem.primary_image_path`
  - Returns `primary_photo.path` or `image_path`.
- `CoinItem.sync_legacy_image_path()`
  - Sets `image_path` to the primary path before saving during compatibility period.

The DTO should live close to `CoinItem`, likely in `coin_collection.py` for Phase 1, unless the implementation review decides to split domain models into a separate module. Keeping it near `CoinItem` reduces Phase 1 blast radius.

## 6. Photo-Role Model

Use role names that work for coins and banknotes without awkward wording.

Recommended canonical roles:

- `FRONT`
- `BACK`
- `HOLDER_FRONT`
- `HOLDER_BACK`
- `EDGE`
- `DETAIL`
- `CERT_LABEL`
- `OTHER`

Role display labels can adapt by collectible type:

- Coin display:
  - `FRONT` can display as "Obverse / Front".
  - `BACK` can display as "Reverse / Back".
- Banknote display:
  - `FRONT` can display as "Front".
  - `BACK` can display as "Back".

Do not use separate coin-only canonical roles such as `OBVERSE` and `REVERSE` as the only stored model. They are useful collector language, but `FRONT` and `BACK` avoid forcing banknotes into coin terminology. If desired, `OBVERSE` and `REVERSE` can be accepted as import aliases and normalized to `FRONT` and `BACK`.

## 7. Backward-Compatibility Strategy

Existing records must continue loading without destructive migration.

Compatibility rules:

- If a record has `image_path` and no `photos`, interpret it as:
  - `photos[0].path = image_path`
  - `photos[0].role = OTHER`
  - `photos[0].is_primary = True`
  - `photos[0].display_order = 0`
  - `photos[0].notes = ""`
- If a record has `photos` and `image_path`, prefer the explicit primary photo in `photos`.
- If `photos` exists but no photo is primary, choose the first photo by display order as primary for display only and report a validation warning.
- If multiple photos are primary, choose the lowest `display_order` as effective primary and report a validation warning.
- If `image_path` differs from the effective primary photo, do not discard either value. During compatibility, update `image_path` only through an explicit save or migration path.
- Old collection files remain readable.
- New collection files remain deterministic.
- No image files are copied, moved, renamed, or deleted as part of schema migration.

## 8. Persistence and Migration Strategy

Use an explicit, idempotent migration path rather than silent destructive rewriting.

Recommended strategy:

1. Add tolerant read support first.
   - `CoinItem.from_dict` accepts old records with only `image_path`.
   - `CoinItem.from_dict` accepts new records with `photos`.
   - Unknown malformed photo entries are ignored or converted to warnings, not crashes.
2. Add deterministic write support.
   - `CoinItem.to_dict` writes `photos` in `display_order`.
   - `image_path` is retained and set to the effective primary path.
3. Add a migration helper.
   - Example conceptual name: `CoinCollection.preview_photo_migration`.
   - Example conceptual name: `CoinCollection.apply_photo_migration`.
   - It should report counts before writing.
   - It should be safe to run more than once.
4. Preserve backups.
   - Existing backup tools should protect `data/collection.json` before any explicit migration.
5. Keep migration reversible where practical.
   - Because no image files move and `image_path` remains, rollback can restore the previous collection JSON from backup or ignore `photos`.

Do not migrate the current collection automatically on ordinary application startup in Phase 1.

## 9. GUI Behavior and Interaction Flow

### Entry-Field Usability

Recommended field widgets:

- Country: editable `ttk.Combobox`
- Denomination: editable `ttk.Combobox`
- Year: editable `ttk.Combobox`
- Grade: editable `ttk.Combobox`

Suggestion sources:

- Existing collection values from all local `CoinItem` records.
- Existing Numista/imported values where present.
- Existing hard-coded grade values already used by the current grade combobox.
- Reference data in the repository only where already present and reliable.

Behavior:

- Typing remains allowed for all fields.
- Unfamiliar manual values are never rejected.
- Country selection may filter denomination suggestions, but only using existing collection/reference data.
- Year suggestions may be filtered by country and denomination when enough local data exists.
- Detection-result population continues setting text variables only.
- Save behavior continues using manual fields as source of truth.
- Clear-form behavior should clear text fields and should be reviewed separately for whether it should clear selected photos.

### Multiple Photos

Recommended main-entry flow:

1. Collector selects one or more image files.
2. The app creates an in-memory photo attachment list for the current unsaved item.
3. The first selected image becomes primary by default.
4. The collector can assign or change roles.
5. The collector can mark a different primary image.
6. The collector can remove, reorder, or relabel photos before saving.
7. The preview area shows the primary photo and a thumbnail strip/list for all selected photos.
8. Saving the item persists structured `photos` and updates `image_path` to the primary path.
9. Item details show all attached photos.

Recommended controls:

- `Add Photos`
- `Remove Photo`
- `Set Primary`
- Role combobox per selected photo
- Notes field per selected photo, optional
- Move up/down controls or drag/reorder if simple to implement safely

Do not block saving because a non-primary photo is missing, but warn when the selected file cannot be read.

## 10. Primary-Image Behavior

The existing collection list and any current display expecting one image should continue using one primary image.

Rules:

- The primary image is the photo with `is_primary=True`.
- Exactly one primary photo should be maintained on save.
- If the collector removes the primary photo and other photos remain, the first remaining photo becomes primary.
- If no photos remain, `image_path` becomes empty only after explicit save.
- `image_path` remains the compatibility alias for primary image during Phase 1.
- Existing reports and displays that use `item.image_path` should continue working.

## 11. Banknote and Coin Compatibility

The model should use neutral photo roles internally while allowing collector-friendly labels.

Recommended approach:

- Store `FRONT` and `BACK`, not coin-only `OBVERSE` and `REVERSE`.
- Display "Obverse / Front" and "Reverse / Back" in coin contexts.
- Display "Front" and "Back" in banknote contexts.
- Allow `EDGE` for coins, tokens, medals, and other objects where applicable.
- Allow `DETAIL`, `CERT_LABEL`, and `OTHER` for both coins and banknotes.
- Do not require a collectible type field before photo support can work.

This preserves unusual coins, tokens, medals, banknotes, colonial issues, and nonstandard denominations.

## 12. Error and Degraded-State Handling

The collection must remain accessible even when photo data is imperfect.

Required behavior:

- Missing image files:
  - Show placeholder text or missing-photo warning.
  - Do not block collection load.
  - Photo Vault reports missing reference.
- Duplicate selected files:
  - Warn and let the collector keep or skip duplicates.
  - Normalize duplicate detection by case-insensitive absolute or normalized path where practical.
- Unsupported image formats:
  - Warn before attaching.
  - Allow only supported image files through the picker by default.
  - Do not crash if legacy data contains unsupported paths.
- Inaccessible OneDrive paths:
  - Treat as missing or inaccessible with a warning.
  - Do not delete path metadata.
- Multiple primary photos:
  - Effective primary is lowest `display_order`.
  - Validation warning recommends fixing.
- No primary photo:
  - Effective primary is first by `display_order`.
  - Save should normalize to exactly one primary.
- Deleted or moved files:
  - Preserve metadata.
  - Show warning in details/audit.
- Malformed legacy photo data:
  - Skip invalid entries with warnings.
  - Preserve raw collection loading where possible.
- Partial migration failure:
  - Abort write.
  - Keep original collection JSON.
  - Report item ids that could not be migrated.
- Manual cancellation of multi-file selection:
  - No state change.
  - No warning needed.

## 15. Regression-Risk Assessment

Risk level: medium-high for multi-photo support, low-medium for editable combobox suggestions.

Primary risks:

- `CoinItem.from_dict(cls, **data)` currently assumes exact schema shape. Adding `photos` without a tolerant loader can break old or mixed records.
- Many engines assume `CoinItem` fields exist and may not expect new required constructor fields.
- `image_path` is used in tests, exports, GUI details, and collection save/load behavior.
- Photo Vault currently counts only `PhotoRecord` records, not item-owned structured photos.
- Existing imports create items with blank `image_path`; these must remain valid.
- The main GUI has one image preview and one current image path. Multi-photo state will require careful state management.
- Full regression is important because the collection model is shared widely.

Mitigation:

- Keep all new DTO fields defaulted.
- Keep `image_path`.
- Add tolerant read before any write migration.
- Add backend tests before GUI implementation.
- Split field suggestions and multi-photo implementation into separate subphases.

## 17. Recommended Implementation Sequence

### Phase 1A: Entry-Field Usability

1. Add suggestion-building helpers to `CoinCollection` or a small GUI-local helper.
2. Replace country, denomination, and year entries with editable `ttk.Combobox` controls.
3. Keep grade as editable combobox and centralize its values.
4. Add country-aware denomination filtering only from existing data.
5. Add tests for suggestion generation and editable/manual values.
6. Verify save, edit, clear-form, detection-result population, and existing record loading behavior.

### Phase 1B: Multi-Photo Data Model

1. Add `ItemPhoto` with defaults.
2. Make `CoinItem.from_dict` tolerant and backward-compatible.
3. Add primary-photo helpers and legacy `image_path` synchronization.
4. Add backend tests for old and new records.
5. Add explicit migration preview/apply helpers.
6. Update CSV export/import compatibility.
7. Update Photo Vault to index/audit item-owned photos.
8. Add Photo Vault tests.

### Phase 1C: Multi-Photo GUI

1. Replace one-image state with a current photo attachment list.
2. Add multi-file selection.
3. Add role, primary, remove, reorder, and preview controls.
4. Save structured photos into `CoinItem.photos`.
5. Update item details to show all attached photos.
6. Verify collection list still uses the primary image compatibility path.
7. Update `USER_GUIDE.md` after implementation is verified.

## 18. Split Recommendation

Keep the umbrella Phase 1 name:

> Faster Collection Entry

Split implementation into Phase 1A and Phase 1B/1C:

- Phase 1A should deliver editable combobox suggestions for country, denomination, year, and grade.
- Phase 1B should deliver the backend multi-photo model, compatibility layer, migration strategy, and Photo Vault integration.
- Phase 1C should deliver the GUI multi-photo workflow.

Reason:

- The combobox work directly reduces repeated keystrokes and is relatively contained.
- Multi-photo support changes the collection schema, compatibility behavior, Photo Vault assumptions, exports, details display, and GUI state model.
- Splitting keeps the mission intact while reducing regression risk.

Do not implement Phase 1 until this design is reviewed and approved.
