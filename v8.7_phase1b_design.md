# v8.7 Phase 1B Design: Multi-Photo Model and Persistence

Design status: proposed for review only.

Implementation status: not started.

Phase 1A baseline:

- Phase 1A complete at `7739412`.
- Full regression baseline: 1,304 tests passing.
- No multi-photo implementation exists.
- `data/collection.json` and `data/debug_feedback.csv` remain local working data and should not be staged as part of Phase 1B.

This document covers backend model, persistence, compatibility, migration, Photo Vault indexing, and import/export design only. It does not approve implementation.

## 1. Exact Current Model and Persistence Behavior

### Collection Item Model

Current file:

- `coin_collection.py`

Current class:

- `CoinItem`

Current persisted photo field:

```text
image_path: str
```

Current `CoinItem` behavior:

- `CoinItem.to_dict()` returns `asdict(self)`.
- `CoinItem.from_dict(data)` calls `cls(**data)`.
- Because `from_dict` is strict, unknown JSON keys can break loading unless the model is changed to tolerate them.
- Because `image_path` is a required constructor argument, old and new records need careful defaults during migration.

Current collection storage:

- `CoinCollection.load_collection()` reads `data/collection.json`.
- Each JSON object is converted with `CoinItem.from_dict(item)`.
- If loading fails, the collection is replaced with an empty in-memory list.
- `CoinCollection.save_collection()` writes a JSON list of `item.to_dict()` objects.

Current import/export behavior:

- `CoinCollection.import_from_csv()` creates `CoinItem(image_path="")`.
- `numista_importer.py` creates `CoinItem(image_path="")`.
- `CoinCollection.export_to_csv()` writes an `image_path` column and does not include structured photo metadata.

### GUI and App Behavior

Current file:

- `coin_collection_gui.py`

Current behavior:

- Main form still uploads one image into `CoinCollectionApp.current_image_path`.
- `CoinCollectionApp.add_to_collection()` saves that one path into `CoinItem.image_path`.
- Item details show one `Image: {item.image_path}` line.
- Phase 1B should not change GUI selection, picker, thumbnail, gallery, or details behavior.

### Photo Vault Behavior

Current file:

- `photo_vault.py`

Current classes:

- `PhotoRecord`
- `PhotoVault`
- `PhotoVaultIntegrityAudit`

Current behavior:

- `PhotoRecord` is metadata-only and stores `file_path`, high-level `photo_type`, linked collection/candidate identifiers, linked coin name, notes, and certification numbers.
- `PhotoVault.collection_photo_statuses()` counts collection photos by `PhotoRecord.linked_collection_item_id`.
- `PhotoVault.coverage_summary()` treats `PhotoRecord` records as the photo source for coverage.
- `PhotoVaultIntegrityAudit` checks `PhotoRecord` records for missing paths, duplicates, invalid extensions, unsupported URL paths, and unlinked records.
- `PhotoVaultIntegrityAudit._collection_coverage_issues()` currently determines whether an item has photos by looking for a linked `PhotoRecord`, not by looking at `CoinItem.image_path`.

### App-State Persistence

Current file:

- `persistence_manager.py`

Current behavior:

- `AppState.photo_records` stores a list of `PhotoRecord` instances.
- `AppState.to_dict()` writes these records under `photo_records`.
- `PersistenceManager.state_from_dict()` restores them with `photo_record_from_dict`.
- This is app runtime state, not the canonical collection item storage.

## 2. Recommended ItemPhoto DTO

Add a small backend DTO close to `CoinItem`, most likely in `coin_collection.py` for Phase 1B.

Recommended dataclass:

```python
@dataclass
class ItemPhoto:
    path: str
    role: str = "OTHER"
    is_primary: bool = False
    notes: str = ""
    display_order: int = 0
```

Recommended behavior:

- `path` is the only required meaningful value.
- `role` is normalized through `PhotoRole`.
- `is_primary` controls compatibility with the existing single-image display.
- `notes` supports backend metadata without requiring GUI changes.
- `display_order` provides deterministic serialization and future GUI ordering.

Recommended methods:

- `ItemPhoto.to_dict()`
- `ItemPhoto.from_dict(row)`
- `ItemPhoto.normalized()`

Normalization should:

- Strip string fields.
- Coerce invalid or missing role to `OTHER`.
- Coerce `is_primary` to bool.
- Coerce invalid `display_order` to deterministic fallback order.
- Never check filesystem existence inside the DTO constructor.

## 3. Recommended PhotoRole Enum

Add a neutral role model that works for coins, banknotes, tokens, medals, slabs, and supporting reference images.

Recommended enum values:

```text
FRONT
BACK
HOLDER_FRONT
HOLDER_BACK
EDGE
DETAIL
CERT_LABEL
OTHER
```

Recommended compatibility aliases:

- `OBVERSE` -> `FRONT`
- `REVERSE` -> `BACK`
- `FRONT_PHOTO` -> `FRONT`
- `BACK_PHOTO` -> `BACK`
- `LABEL` -> `CERT_LABEL`
- Empty or unknown value -> `OTHER`

Reason:

- `FRONT` and `BACK` are neutral across coins and banknotes.
- Coin-specific terms can remain display labels later in Phase 1C.
- The backend does not need a collectible-type field to support photos.

## 4. Source-of-Truth Ownership

Recommended source of truth:

- Collection-item photo attachments belong to `CoinItem.photos` in `data/collection.json`.

Recommended boundary:

- `CoinItem.photos` owns photo attachments for owned collection items.
- `CoinItem.image_path` remains a compatibility alias for the primary photo path.
- `PhotoVault` indexes and audits collection-item photos.
- `PhotoVault` continues to own app-state metadata for candidate, reference, auction, sold, and supplemental photo records through `PhotoRecord`.
- `PersistenceManager.AppState.photo_records` remains app-state storage and should not become the canonical storage for owned item photos.

Reason:

- Owned item photos are part of the item record.
- Splitting canonical item photo state between `data/collection.json` and `collection_data/app_state/app_state.json` would create drift and unclear restore behavior.

## 5. `image_path` Compatibility Rules

`image_path` must remain readable and writable through Phase 1B.

Rules:

1. Existing records with only `image_path` continue loading.
2. Existing records with blank `image_path` continue loading.
3. New records may include both `image_path` and `photos`.
4. Effective primary image is derived from `photos` when `photos` exists.
5. `image_path` mirrors the effective primary image during deterministic write.
6. If `photos` is missing or empty and `image_path` is non-empty, the effective photo list is one legacy photo:
   - `path = image_path`
   - `role = OTHER`
   - `is_primary = True`
   - `display_order = 0`
   - `notes = ""`
7. If `photos` has no primary, the first photo by `display_order` is effective primary.
8. If multiple photos are primary, the first photo by `display_order` is effective primary.
9. Invalid photo metadata should not delete `image_path`.
10. No image files are moved, copied, renamed, or deleted by compatibility logic.

Recommended helpers:

- `CoinItem.normalized_photos()`
- `CoinItem.primary_photo()`
- `CoinItem.primary_image_path`
- `CoinItem.sync_image_path_from_primary()`

## 6. Serialization Format

Recommended JSON shape:

```json
{
  "id": "coin_20260711_120000",
  "image_path": "coin_photos/collection/Canada/1920_1c_front.jpg",
  "photos": [
    {
      "path": "coin_photos/collection/Canada/1920_1c_front.jpg",
      "role": "FRONT",
      "is_primary": true,
      "notes": "",
      "display_order": 0
    },
    {
      "path": "coin_photos/collection/Canada/1920_1c_back.jpg",
      "role": "BACK",
      "is_primary": false,
      "notes": "",
      "display_order": 1
    }
  ],
  "country": "Canada",
  "denomination": "1 cent",
  "year": "1920",
  "grade": "VF-20"
}
```

Serialization requirements:

- Preserve existing top-level fields.
- Add `photos` as a list.
- Sort photos by `display_order`, then path, for deterministic output.
- Emit exactly one `is_primary: true` when photos exist.
- Keep `image_path` as the primary path.
- Use only relative or user-provided paths; do not rewrite path roots.
- Do not write migration metadata into each item unless a later review approves it.

## 7. Legacy-Read Behavior

`CoinItem.from_dict` must become tolerant before new writes are introduced.

Required behavior:

- Ignore unknown JSON keys or preserve only known fields.
- Supply defaults for missing optional fields.
- Convert absent `photos` to an empty stored list, while `normalized_photos()` interprets legacy `image_path`.
- Accept malformed `photos` values without crashing collection load.
- Skip malformed individual photo rows with warnings where a warning channel exists.
- Preserve enough data to avoid silent photo-path loss.

Important implementation constraint:

- Do not keep the current `cls(**data)` behavior once `photos` is introduced; it is too brittle for mixed-schema files.

Recommended read sequence:

1. Validate `data` is a dict.
2. Extract known `CoinItem` fields with defaults.
3. Parse `photos` with `ItemPhoto.from_dict`.
4. Normalize primary state in memory.
5. Keep `image_path` unchanged until explicit save or migration.

## 8. Migration Strategy

Migration must be explicit, idempotent, and non-destructive.

Recommended migration stages:

### Stage 1: Tolerant Read

- App can load old records and new records.
- No write format change required unless the user saves.

### Stage 2: Deterministic Write

- Saving a collection writes `photos` and `image_path`.
- Existing records without photos get derived legacy photos only when save/migration is explicit.

### Stage 3: Explicit Migration Helper

Recommended APIs:

```text
CoinCollection.preview_photo_migration()
CoinCollection.apply_photo_migration()
```

Preview should report:

- total items
- items with legacy `image_path`
- items with existing `photos`
- items with blank image fields
- malformed photo rows
- multiple-primary cases
- no-primary cases
- duplicate photo paths

Apply should:

- Require an explicit call.
- Be idempotent.
- Create structured `photos` for legacy image paths.
- Preserve `image_path`.
- Not copy or move files.
- Return a structured result object with counts and warnings.

Rollback:

- Use existing backup package or pre-migration JSON copy.
- Because files are not moved and `image_path` remains, ignoring `photos` remains practical.

Do not auto-migrate `data/collection.json` on ordinary startup.

## 9. Photo Vault Integration

Photo Vault should index item-owned photos while preserving existing `PhotoRecord` behavior.

Recommended approach:

- Add a conversion adapter from `CoinItem.photos` to audit/index records.
- Do not force item-owned photos into `AppState.photo_records`.
- Keep `PhotoRecord` for non-owned and supplemental metadata.

Possible adapter:

```text
PhotoVault.item_photos_for(item) -> List[PhotoRecord-like records]
PhotoVault.collection_photo_records() -> combined item-owned + supplemental collection records
```

Coverage behavior:

- An item has photos if `CoinItem.normalized_photos()` returns at least one path, or if supplemental `PhotoRecord` links exist.
- `PhotoCoverageSummary.total_photos` should include item-owned photos plus supplemental records, with duplicate handling clearly defined.
- Missing/broken path checks should apply to item-owned photo paths and `PhotoRecord.file_path`.
- Duplicate path checks should consider the combined set.

Compatibility:

- Existing tests that pass only `PhotoRecord` must continue passing.
- Existing app-state photo records remain searchable/exportable.
- Candidate/reference/auction/sold records remain `PhotoRecord`-owned.

### Numista Import

Recommended Phase 1B export behavior:

  - or `photo_count`

Recommendation:

- For Phase 1B, avoid changing CSV export shape beyond ensuring `image_path` remains the primary path.

## 11. Error Handling

Collection load must degrade gracefully.

Required behavior:

- Missing image files:
  - Load item.
  - Preserve path metadata.
  - Report through Photo Vault/audit, not collection load failure.
- Unsupported image formats:
  - Load item.
  - Photo Vault flags invalid extension.
- Inaccessible OneDrive paths:
  - Load item.
  - Treat as missing/inaccessible in audit.
- Duplicate photo paths:
  - Preserve data.
  - Audit reports duplicates.
- Multiple primary photos:
  - Effective primary is deterministic.
  - Save normalizes to one primary.
- No primary photo:
  - Effective primary is deterministic.
  - Save normalizes to one primary.
- Malformed `photos` root:
  - Treat as no structured photos.
  - Preserve `image_path`.
- Malformed photo row:
  - Skip row or coerce safely.
  - Do not fail entire collection load.
- Partial migration failure:
  - Do not write collection file.
  - Return error list and affected item ids.
- Blank path:
  - Do not create meaningful photo entry.
  - Keep item loadable.

## 14. Regression Risks

Risk level: medium-high.

Primary risks:

- Strict `CoinItem.from_dict(cls(**data))` can break mixed-schema reads if not replaced carefully.
- `asdict(self)` may emit enum objects incorrectly unless DTO serialization is explicit.
- Many tests instantiate `CoinItem` directly; new fields must have safe defaults.
- Existing code may expect `image_path` to be a string and present.
- Photo Vault coverage semantics may change if item-owned photos and `PhotoRecord` records are double-counted.
- CSV export can break if `writer.writerow(item.to_dict())` receives keys not present in `fieldnames`.
- Importers may break if `CoinItem` constructor changes without defaults.
- App-state photo records may become ambiguous if source-of-truth boundaries are not explicit.
- Current production collection has existing records that must remain loadable.

Mitigation:

- Add defaults for every new field.
- Replace strict deserialization before emitting new schema.
- Keep `image_path`.
- Keep CSV fieldnames stable.
- Do backend tests before Photo Vault changes.
- Keep Phase 1B free of GUI changes.
- Run full regression before commit.
