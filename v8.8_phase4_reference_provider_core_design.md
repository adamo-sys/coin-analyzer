# v8.8 Phase 4 Design: Canadian Reference Provider Core

Status: Design only  
Implementation: Not started  
Baseline: `8543065` with 1,438 tests passing  
Umbrella document: `v8.8_canadian_reference_intelligence_design.md`

## Phase Name

Canadian Reference Provider Core

## 1. Root-Cause Analysis

Coin Analyzer now has a complete photo-readiness vertical slice:

```text
Photos
-> deterministic readiness checks
-> CollectorWorkspace report
-> read-only GUI
-> export
```

The next natural product question is:

> If the photos are good enough, what reference knowledge can they be compared against?

The risky mistake would be jumping directly into catalogue ingestion or identification. That would mix legal questions, source attribution, data modelling, matching, and GUI behavior in one step.

Phase 4 should solve only the reference-data foundation:

- how providers expose issue records
- how records preserve source attribution
- how conflicts are represented
- how local/manual/open-provider boundaries work
- how validation stays deterministic

This lets future Canadian Reference Intelligence consume lawful, attributed, structured data without binding the architecture to any one catalogue.

## 2. Relationship To Broader Canadian Reference Intelligence Design

`v8.8_canadian_reference_intelligence_design.md` remains the umbrella vision for:

- candidate identification
- evidence-based explanations
- rarity context
- possible value-by-grade context when licensed or user-provided
- future Collector Copilot behavior

This Phase 4 document is narrower. It creates the provider core that the broader design would eventually use.

Phase 4 does not rank photographed coins, identify coins, parse OCR, grade coins, estimate market value, or ingest commercial catalogues.

Recommended layering:

```text
Phase 4 Provider Core
-> Future Reference Aggregation / Search
-> Future Candidate Identification
-> Future Explainable Identification
-> Future Collector Copilot
```

## 3. Current Reusable Architecture

Useful repository patterns:

- dataclass DTOs with `to_dict()` methods
- enum-like constants or `Enum` classes for constrained values
- deterministic report ordering
- validation reports that collect warnings instead of crashing
- local-file connectors that avoid scraping and external APIs
- source summaries and markdown exporters
- aggregation layers that isolate failing sources
- strong ownership-boundary comments in modules such as `connected_data.py`

Relevant existing style:

- `listing_connectors.py` uses local-file connectors, validation reports, source summaries, and deterministic normalization.
- `connected_data.py` uses DTOs, enums, no mutation, and explicit ownership boundaries.
- `collector_workspace.py` uses provider/engine lifecycle lazily and reports degraded states rather than leaking implementation errors upward.

Phase 4 should follow those conventions.

## 4. Ownership Boundary

Owns:

- reference provider protocol
- Canadian issue DTOs
- reference source/provenance DTOs
- provider capability DTOs
- validation reports
- conflict DTOs
- local/manual/open provider boundaries
- deterministic aggregation rules
- local JSON schema definition

Does not own:

- collection items
- photo files
- OCR output
- image assessment output
- GUI display
- CollectorWorkspace integration
- identification/candidate ranking
- grading
- pricing
- commercial catalogue content

The provider core should be a library layer. It should not reach into GUI, OCR, Photo Vault, Image Assessment, or collection persistence.

## 5. Public API

Smallest useful public API:

```python
class ReferenceProvider:
    def provider_id(self) -> str: ...
    def capabilities(self) -> ReferenceProviderCapabilities: ...
    def get_source_metadata(self) -> ReferenceSource: ...
    def validate(self) -> ReferenceValidationReport: ...
    def get_issue(self, issue_id: str) -> Optional[ReferenceRecord]: ...
    def search(self, query: ReferenceQuery) -> ReferenceSearchResult: ...
    def list_issues(self, filters: Optional[ReferenceFilters] = None) -> ReferenceSearchResult: ...
```

Recommended choices:

- synchronous API
- immutable returned records by convention
- no pagination in Phase 4A/4B unless local files prove large enough to need it
- deterministic ordering by normalized country, denomination, year/date text, variety, and issue id
- errors returned through validation/report DTOs where possible
- provider failures isolated by aggregation layer

Avoid:

- async complexity
- network calls
- provider-specific public methods
- direct mutation methods
- hidden global registries

### CanadianIssue

Neutral issue DTO, not tied to any one catalogue.

```python
@dataclass(frozen=True)
class CanadianIssue:
    issue_id: str
    country: str = "Canada"
    authority: str = ""

    year: str = ""
```

## 7. Provider Capability Model

`ReferenceProviderCapabilities` should be explicit:

```python
@dataclass(frozen=True)
class ReferenceProviderCapabilities:
    provider_id: str
    source_type: ReferenceSourceType
    capabilities: List[ReferenceProviderCapability] = field(default_factory=list)
    supports_field_provenance: bool = False
    supports_conflicts: bool = False
    supports_filters: bool = False
    mutable: bool = False
    network_required: bool = False
    licence_required: bool = False
```

Rules:

- Phase 4 providers should have `network_required=False`.
- Commercial future adapters should set `licence_required=True`.
- Manual provider may be mutable in memory but should not write files unless a later persistence phase approves it.
- Local JSON provider should be read-only unless explicit save/export support is added later.

## 8. Provenance And Attribution Model

Every returned fact must preserve provenance.

Recommended model:

- `ReferenceRecord.source` gives record-level provenance.
- `CanadianIssue.source_refs` gives field-level provenance where known.
- Each `SourceRef` may name the field, raw value, normalized value, and source record id.
- `catalogue_numbers` should retain catalogue namespace, for example:
  - `"manual": "M-001"`
  - `"synthetic": "TEST-1920-CENT"`
  - future licensed namespaces only after permission

Multiple sources:

- never silently overwrite
- preserve all `ReferenceRecord` objects
- aggregate into conflict reports when values differ
- source priority may be an explicit future policy, not an implicit default

User overrides:

- represented as manual-source records
- source type: `MANUAL`
- should not erase source claims from other providers
- can be shown as an explicit collector override in future UI/reporting

Attribution display should be future-ready:

```text
Source: Manual Reference Data
Edition: 2026 local
Licence: User-entered
Attribution: Entered by collector
```

## 9. Conflict Model

Do not choose winners automatically.

Recommended DTO:

```python
@dataclass(frozen=True)
class ReferenceConflict:
    issue_key: str
    field_name: str
    conflict_type: ReferenceConflictType
    claims: List[SourceRef] = field(default_factory=list)
    notes: str = ""
```

Conflict rules:

- mintage disagreement: preserve all claims
- weight/diameter disagreement: preserve raw values and normalized values if available
- composition disagreement: preserve all strings and normalized tokens
- variety-name disagreement: preserve all source names and aliases
- catalogue-number disagreement: preserve by catalogue namespace
- date-range disagreement: preserve all date text

Aggregation should expose conflicts as metadata, not mutate issue fields.

Future resolution policies may include:

- prefer manual source
- prefer licensed source
- prefer most recent edition
- prefer source priority list

No such policy should be implicit in Phase 4.

## 10. Normalization Model

Normalization must be deterministic and non-destructive.

General rule:

```text
raw source text remains available
normalized values support search/filter/grouping
```

Suggested helpers:

- `normalize_country("CAN", "Canada") -> "canada"`
- `normalize_authority("Dominion of Canada") -> "dominion of canada"`
- `normalize_denomination("1 Cent", "cent") -> "1 cent"`
- `normalize_year("1920") -> "1920"`
- `normalize_date_text("1920-21") -> "1920-21"`
- `normalize_mintmark("H") -> "h"`
- `normalize_composition("Bronze") -> "bronze"`
- `normalize_measurement("3.24 g") -> ("3.24", "g")` if implemented
- `normalize_variety("Near 6") -> "near 6"`
- `normalize_catalogue_id("KM# 28") -> "km:28"` if namespace is known

Do not:

- infer missing values
- convert uncertain date ranges into single years
- convert every measurement into floats unless raw value is retained
- treat variant spelling as authoritative correction

- provider should not crash aggregation

## 12. Manual-Provider Behavior

Manual provider purpose:

- represent user-entered or user-owned reference data
- support overrides without erasing other source claims
- allow tests and future GUI/manual workflows

Phase 4 behavior:

- initialize from in-memory records or local JSON data
- validate records deterministically
- search and filter records
- expose `ReferenceSource` as `MANUAL`
- optionally expose `mutable=True` capability for in-memory editing, but do not persist unless a later phase approves it

Manual provider should be legally safe because the collector controls entered content. Tests must still use synthetic data.

## 13. Error Handling

Expected errors:

- malformed JSON
- unsupported schema version
- missing source metadata
- duplicate issue IDs
- duplicate source IDs
- incomplete records
- invalid units
- conflicting records
- unavailable provider
- empty provider
- corrupted local file
- provider exception during search or lookup

Handling rules:

- validation returns `ReferenceValidationReport`
- search/list operations return warnings where possible
- one bad provider must not crash aggregation
- aggregation should include provider-level warning metadata
- exceptions should be caught at provider aggregation boundaries
- stack traces should not be part of user-facing report data

## 16. Regression Risks

Risks:

- accidentally creating a scraper
- accidentally encoding one commercial catalogue as the internal model
- mixing identification logic into provider search
- allowing one source to silently overwrite another
- losing raw source text during normalization
- creating fixtures from copyrighted/proprietary catalogue content
- adding network behavior under an "open provider" name
- making manual overrides destructive
- coupling provider core to GUI or CollectorWorkspace too early

Mitigations:

- local/manual providers first
- synthetic fixtures only
- explicit source metadata required
- field-level provenance where available
- conflict DTOs rather than winner selection
- no network access in tests
- out-of-scope list enforced in implementation review

## 19. Recommendation: Split Phase 4

Phase 4 should be split into three implementation slices:

```text
4A - DTOs, provider protocol, validation
4B - local JSON/manual providers
4C - aggregation/conflict handling
```

Reason:

- 4A establishes the legal and architectural boundary.
- 4B proves the model with local/manual data and synthetic fixtures.
- 4C introduces multi-provider complexity only after records and provenance are stable.

Do not ship this as one large implementation slice. The legal boundary and conflict model are too important to bury inside a broad provider implementation.
