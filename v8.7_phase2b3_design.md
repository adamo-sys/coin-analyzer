## 2. Search and Select Interaction Flow

Recommended flow:

1. Collector opens `Collector Home -> Photo Inbox...`.
2. Collector refreshes the inbox.
3. Collector selects a pending Photo Set.
4. Collector clicks `Attach to Existing`.
5. Coin Analyzer opens a focused attach dialog.
6. Collector searches collection records.
7. Search results show a compact item summary.
8. Collector selects the target collectible.
9. Dialog previews:
   - target item summary
   - existing target photos
   - incoming Photo Set photos
   - duplicate warnings, if any
10. Collector clicks `Attach Photos`.
11. Coin Analyzer merges incoming photo references into `CoinItem.photos`.
12. Coin Analyzer saves the item.
13. Only after save succeeds, Coin Analyzer marks the Photo Set `ATTACHED`.
14. Photo Inbox refreshes.

No manual Browse dialog should be required.

## 3. Target-Item Confirmation Flow

The confirmation view should make the target unmistakable.

Recommended target summary:

```text
Target Collectible
ID: coin_...
Country: Canada
Denomination: 1 cent
Year: 1920
Grade: VF-20
Current Photos: 2
Primary Image: C:\...\front.jpg
```

Recommended incoming summary:

```text
Incoming Photo Set
Photos: 3
Suggested Label: IMG_2041 / IMG_2043
State: NEW
```

The attach action should remain disabled until a target item is selected.

If the search result is ambiguous, the collector decides. The app should not infer the target item from filenames, OCR, or similarity in Phase 2B.3.

## 4. Photo Merge Rules

Core rule:

- Append incoming Photo Set photos to the existing item photos.
- Do not replace existing photos.
- Do not replace existing primary image automatically.

Recommended merge algorithm:

1. Load existing photos with `item.normalized_photos()`.
2. Capture existing primary path, if any.
3. Build incoming `ItemPhoto` objects from the Photo Set paths.
4. Remove incoming paths that already exist on the item.
5. Append remaining incoming photos after existing photos.
6. Set appended `display_order` after the last existing photo.
7. Keep existing primary photo as primary.
8. If the item has no existing photos or no effective primary, make the first merged photo primary.
9. Normalize via existing photo helpers.
10. Save updated `photos` and `image_path`.

The merge should be metadata-only.

No source image file should be copied, moved, renamed, archived, or deleted.

## 5. Duplicate Detection Behavior

Duplicate detection should use path identity, not image content.

Recommended duplicate key:

- `os.path.normcase(os.path.abspath(path))`

Behavior:

- If an incoming photo path already exists in the target item photos, skip it.
- Show a concise warning/count in the preview.
- If all incoming photos are duplicates, disable final attach or show "No new photos to attach."
- Do not mark the Photo Set `ATTACHED` if no new photo was saved, unless the collector explicitly confirms "Mark as handled."

Recommendation for Phase 2B.3:

- If all photos are duplicates, do not attach and do not mark the Photo Set attached.
- Let the collector choose `Ignore` separately from the inbox if the set is redundant.

## 6. Role and Default Assignment Strategy

Existing photos:

- Preserve existing roles exactly.
- Preserve existing notes.
- Preserve existing display order.
- Preserve existing primary selection.

New incoming photos:

- Assign conservative defaults using existing Phase 1C behavior:
  - first new photo: `FRONT`
  - second new photo: `BACK`
  - remaining new photos: `OTHER`
- If future inbox metadata supports better roles, that can be considered later.
- Do not infer content recognition from filenames.

If the target already has a `FRONT` or `BACK` photo, still use conservative defaults for the new incoming photos. The collector can relabel in the existing edit flow.

## 7. Primary-Image Behavior

Product rule:

- Never replace the existing primary image automatically when attaching to an existing item.

Behavior:

- If the target item already has an effective primary, keep it.
- Newly attached photos should not become primary by default.
- If the target item has no photos and no `image_path`, the first incoming photo may become primary.
- If the target item has legacy `image_path` only, treat that synthesized photo as existing primary and preserve it.

Reason:

- Primary image is a collector-facing display decision.
- Attachment should add evidence, not silently change the item identity in the UI.

## 8. Save-Success Behavior

Save should be transactional at the workflow level:

1. Merge photos in memory.
2. Attempt `collection.update_item(...)`.
3. If update succeeds:
   - call `manager.mark_attached(photo_set_id, item_id=target_item.id)`
   - refresh Photo Inbox rows
   - refresh collection list if needed
   - close or update attach dialog
4. If update fails:
   - do not mark Photo Set attached
   - keep the Photo Set pending
   - show a clear error

Inbox state should transition exactly once.

Repeated callbacks must not duplicate attached photos or reprocess the Photo Set.

## 9. Cancel and Failure Behavior

Cancel behavior:

- Closing attach dialog changes nothing.
- Changing search text changes nothing.
- Selecting a target changes nothing.
- Previewing merge changes nothing.

Failure behavior:

- Missing target item: no change.
- No Photo Set selected: no change.
- No non-duplicate incoming photos: no collection save, no inbox transition.
- `update_item` failure: no inbox transition.
- `mark_attached` failure after item save:
  - show warning that item was updated but inbox state was not marked.
  - leave Photo Set visible until the next manual action or retry.

The design does not require rollback of a successful item save if marking the inbox fails. That would be heavier than the current app architecture supports.

## 10. Inbox State Transitions

Allowed Phase 2B.3 transition:

```text
NEW / DEFERRED / ERROR
-> user clicks Attach to Existing
-> user selects target
-> user confirms Attach Photos
-> collection update succeeds
-> ATTACHED
```

Do not transition on:

- opening Photo Inbox
- selecting Photo Set
- opening attach dialog
- searching collection
- selecting target item
- previewing target
- cancelling dialog
- duplicate-only preview
- failed collection update

Terminal states:

- `ATTACHED`, `IMPORTED`, and `IGNORED` should not appear as attach candidates.

## 13. Regression Risks

Primary risks:

- Accidentally replacing an existing primary image.
- Accidentally duplicating photo references.
- Marking Photo Set attached before item save succeeds.
- Saving the item but failing to mark inbox state.
- Attaching to the wrong item due to weak search UI.
- Mutating collection data during preview.
- Making Attach to Existing too complex for the current GUI.
- Starting Phase 2C file-management behavior accidentally.

Mitigations:

- Keep merge helper pure and unit-tested.
- Require explicit target selection.
- Show target summary before attach.
- Append only.
- Preserve primary unless no primary exists.
- Use path-based duplicate detection.
- Transition inbox state only after `update_item` succeeds.
- Keep file references in place.

## Recommendation

Approve Phase 2B.3 as a narrow attach-to-existing workflow.

The strongest product rule is:

```text
Attach appends evidence. It does not redefine the collectible.
```

Therefore, existing photos, roles, notes, order, and primary image should remain intact unless the collector deliberately edits them later.
