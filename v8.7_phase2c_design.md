## 1. Root-Cause Analysis

Phase 2B made the Photo Inbox useful after the collector opens it. The remaining friction is remembering to open it.

Current workflow:

```text
Take photos
->
Share / Add to Coin Analyzer
->
OneDrive / Pictures / Uploads
->
Collector manually remembers to open Photo Inbox
```

The weak point is now awareness, not processing capability. Coin Analyzer can already scan, group, review, create new collectibles, and attach photos to existing collectibles. The collector should not have to keep a mental note that new photos may be waiting.

Phase 2C should answer one question:

```text
Are there pending Photo Sets that deserve the collector's attention?
```

It should not answer:

```text
What should be imported automatically?
```

The collector remains in control.

## 2. Startup Flow

Recommended startup behavior:

1. Coin Analyzer launches.
2. If `scan_photo_inbox_on_startup` is enabled, run one lightweight `PhotoInboxManager.refresh()` after the main window is initialized.
3. Count pending Photo Sets from `manager.get_pending_sets()`.
4. Update a visible Photo Inbox indicator.
5. If pending sets exist and notifications are enabled, show a non-blocking notice or a single low-friction prompt.
6. Do not open Photo Inbox automatically unless the collector clicks the notification or indicator.

Recommended default:

- Scan on startup: enabled.
- Show pending notification: enabled.
- Auto-refresh inbox when opened: enabled.
- Background monitoring: disabled and not implemented.

Rationale:

- Startup scan removes the "remember to check" burden.
- A single scan is deterministic and testable.
- The collector still chooses the next action.
- No filesystem watcher means no cloud-sync race conditions, no hidden imports, and no continuous background behavior.

Startup scan failure should degrade quietly:

- Keep the application usable.
- Show "Photo Inbox unavailable" or similar status text.
- Preserve the existing manual Photo Inbox path.
- Do not block launch.

## 3. Notification Strategy

Recommended notification hierarchy:

1. Persistent indicator:
   - Add a small Photo Inbox count in an existing visible area.
   - Example: `Photo Inbox (3)`.
   - Clicking it opens the existing Photo Inbox window.

2. Startup notice:
   - Show only when pending Photo Sets exist.
   - Example: `3 new Photo Sets detected.`
   - Provide a direct `Open Photo Inbox` action.
   - Provide a dismiss action.

3. Dismissal memory:
   - Remember the last dismissed pending-set signature or count for the current app session.
   - Do not repeatedly prompt for the same pending state during one session.
   - If the pending count changes, a new notification is allowed.

Avoid modal interruption as the default. A modal prompt is acceptable only if the existing GUI patterns make non-modal notification impractical in Phase 2C. If a modal prompt is used, it should be one prompt at startup only, with clear options:

- Open Photo Inbox
- Later

Recommended wording:

```text
Photo Inbox

3 pending Photo Sets are ready to review.
```

Avoid:

- "Import now"
- "Process automatically"
- "Detected coins"

The app has detected pending photo sets, not coin identities.

## 5. Configuration

Recommended settings:

- `scan_photo_inbox_on_startup`
  - Default: `true`.
  - Runs one startup refresh.

- `show_photo_inbox_startup_notification`
  - Default: `true`.
  - Shows a startup notice only when pending sets exist.

- `auto_refresh_photo_inbox_when_opened`
  - Default: `true`.
  - Preserves the existing behavior where opening Photo Inbox refreshes the inbox.

- `photo_inbox_notification_dismissed_signature`
  - Session-only by default.
  - Optional persistent setting if users report repeated reminders across launches are annoying.

Configuration storage options:

- Prefer the existing app preference/configuration mechanism if one already exists.
- If no suitable preference layer is available, keep Phase 2C defaults hardcoded and defer a settings UI.
- Do not introduce a new broad settings architecture for Phase 2C.

No background watcher:

- No filesystem watch service.
- No polling loop.
- No cloud-provider integration.
- No automatic import.

## 6. Test Plan

Focused tests should cover:

- Startup scan disabled:
  - No `PhotoInboxManager.refresh()` call.
  - Indicator remains neutral or uses existing state only.

- Startup scan enabled:
  - Runs one refresh.
  - Pending count updates.

- Pending sets exist:
  - Indicator displays count.
  - Startup notification is eligible.

- No pending sets:
  - Indicator displays no count.
  - No startup notification.

- Notification disabled:
  - Count updates.
  - No prompt/notice shown.

- Notification dismissal:
  - Dismissing suppresses repeated prompt for the same pending state during the same session.
  - A changed pending count can show a new notice.

- Photo Inbox opened from indicator:
  - Calls existing `open_photo_inbox`.

- Auto-refresh when opened enabled:
  - Existing inbox refresh behavior is preserved.

- Auto-refresh when opened disabled:
  - Photo Inbox can still be opened.
  - Manual refresh remains available.

- Startup scan failure:
  - Application launch is not blocked.
  - Indicator/status shows a safe fallback.

- Full regression:
  - `python -m unittest discover`

Recommended new focused test file:

- `test_phase2c_photo_inbox_notifications.py`

## 8. Regression Risks

Startup performance:

- A scan during launch could make the app feel slower if the inbox folder is large or on a syncing provider.
- Mitigation: run one lightweight scan after the main window initializes, keep errors non-blocking, and preserve manual refresh.

Notification fatigue:

- Repeated prompts could become annoying.
- Mitigation: session-level dismissal signature.

False urgency:

- The app may imply photos are coins when they are only pending files.
- Mitigation: use "Photo Sets" language, not "coins detected."

Cloud-sync timing:

- OneDrive or another folder may still be writing files during startup.
- Mitigation: rely on existing file-stability logic and leave files referenced in place.

Accidental automation:

- A notification could drift into automatic import behavior.
- Mitigation: notification opens Photo Inbox only; it never creates, attaches, ignores, moves, copies, or deletes.

GUI clutter:

- Another visible count could make the main screen feel noisy.
- Mitigation: use a compact indicator and reuse Collector Home/Photo Inbox surfaces.

State mismatch:

- Indicator count could become stale after Create New, Attach, Ignore, or Defer.
- Mitigation: refresh the count after existing Photo Inbox actions and after closing or updating the inbox.

2. Add focused tests for helper behavior.

4. Add startup scan scheduling after the main window is initialized.

5. Add startup notification behavior behind the notification setting.

6. Wire the indicator to the existing `open_photo_inbox`.

7. Refresh the indicator after Photo Inbox actions that change Photo Set state.

8. Add optional configuration defaults using existing preference patterns.

9. Run focused tests.

10. Run full unittest discovery.

11. Commit Phase 2C only.

12. Stop before any Phase 2D, watcher, file-management, OCR, or grading work.
