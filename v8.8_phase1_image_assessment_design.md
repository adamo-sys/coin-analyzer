# v8.8 Phase 1 Design: Image Assessment Layer

Design status: approved.

Implementation status: implemented in v8.8 Phase 1.

Baseline:

- v8.7 includes editable collection-entry suggestions.
- v8.7 includes `CoinItem.photos` as the backward-compatible structured photo source of truth.
- v8.7 includes multi-photo entry and item-detail gallery support.
- v8.7 includes Photo Inbox backend, review window, Create New, Attach Existing, and startup awareness.
- Latest known regression baseline: approximately 1,393 tests passing.

This document records the approved v8.8 Phase 1 Level A implementation boundary. It does not approve GUI work, OCR changes, identification, grading, catalogue ingestion, machine learning, or external services.

## 1. Root-Cause Analysis

Coin Analyzer is moving toward Canadian reference intelligence and eventual grading-readiness advice. Both depend on photo evidence quality.

The current collector workflow can already attach multiple photos, organize incoming Photo Sets, and send photos toward OCR or review. The remaining risk is that downstream engines may attempt analysis on photos that are missing, blurred, too small, one-sided, overexposed, or unsuitable for the requested task.

The product problem is not "identify better" yet. It is:

```text
Before analysis, decide whether the photo evidence is good enough for that analysis.
```

The Image Assessment Layer should answer:

1. Are the photographs usable?
2. Which quality problems are present?
3. What additional or replacement photographs are needed?
4. Which downstream analyses are safe to attempt?
5. How confident should Coin Analyzer be in that readiness judgment?

The layer evaluates photograph suitability only. It must not identify, attribute variety, grade, price, or recommend certification.

## 2. Current Reusable Architecture

Inspected files:

- `coin_collection.py`
- `coin_collection_gui.py`
- `image_analyzer.py`
- `coin_recognition.py`
- `ocr_assisted_identification.py`
- `ai_grading_assistant.py`
- `photo_vault.py`
- `collector_workspace.py`
- `connected_data.py`
- related photo and grading DTO modules

Reusable pieces:

- `CoinItem.photos`
  - Current structured source of truth for item-owned photos.
  - Provides ordered `ItemPhoto` metadata with role, primary flag, notes, and path.
  - Synthesizes legacy `image_path` records for backward compatibility.

- `PhotoRole`
  - Existing role vocabulary for `FRONT`, `BACK`, holder photos, detail photos, certification label, and other.
  - Should be reused rather than creating a second role system.

- `PhotoVault`
  - Metadata/index/audit layer for photo references.
  - Already handles missing references, duplicate references, coverage, and certified-item photo coverage.
  - Should remain an indexing/audit layer, not a readiness engine.

- `PhotoCoverageReport` and `PhotoVaultIssue`
  - Useful report style: counts, findings, recommendations, `to_dict()`, markdown formatting.

- `PhotoCaptureWorkflow`
  - Already models front/back capture sessions and `ready_for_ocr` metadata.
  - Useful for vocabulary and future integration, but readiness in Phase 1 should not depend on phone-capture sessions.

- `CoinGrader.analyze_image_quality(image_path)`
  - Existing deterministic image-quality helper for sharpness, contrast, and brightness.
  - This is the strongest immediate reuse candidate.
  - It should be treated as a generic quality metric provider, not as grade evidence.

- `ConnectedDataEngine`
  - Demonstrates a thin, read-only cross-reference boundary with no ownership of upstream data.
  - Image Assessment should follow a similar non-mutating pattern.

- `CollectorWorkspace`
  - Current workspace aggregation layer is view-model oriented and avoids business logic.
  - Future integration should expose assessment reports there without coupling the engine to Tkinter.

Existing code to avoid expanding in Phase 1:

- `image_analyzer.py`
  - Combines recognition and grading paths.
  - Not an appropriate home for a new readiness gate because it already reaches into identification and grade outputs.

- `coin_recognition.py`
  - Uses Hough circles, segmentation, OCR variants, country/denomination/year detection, and writes date-crop debug outputs.
  - Useful evidence that advanced visual paths exist historically, but Phase 1 should not extend this layer.

- `coin_grading.py`
  - Contains quality metrics, but also attempts surface issue, luster, wear, and grade estimation.
  - Phase 1 should reuse only basic deterministic image quality metrics and should not reuse or bless condition claims.

- `ai_grading_assistant.py`
  - Explicitly says deterministic, advisory-only, no computer vision, no ML, no collection mutation.
  - Image Assessment should preserve that guardrail and later become an input gate to grading workflows.

## 3. Recommended Ownership Boundary

Recommended new owner:

```text
ImageAssessmentEngine
```

Responsibilities:

- assess individual photo files
- assess an ordered photo set
- classify evidence quality by downstream task
- emit deterministic DTO reports
- never mutate collection items, Photo Vault records, Photo Inbox state, or files
- never call OCR, identification, grading, catalogue providers, external APIs, or GUI code

Non-owners:

- `CoinItem`
  - Owns collection photo metadata only.

- `PhotoVault`
  - Owns indexing/audit coverage only.

- `CoinRecognizer`
  - Owns older identification-oriented CV behavior only.

- `AIGradingAssistant`
  - Owns grading guidance only.

- `CollectorWorkspace`
  - May aggregate reports later, but should not contain readiness logic.

Recommended file:

```text
image_assessment.py
```

Phase 1 should be engine/model only.

Input sources:

- `ItemPhoto`

Output:

- serializable with `to_dict()`

Not allowed:

- Tkinter dependencies
- collection mutation
- photo movement
- OCR invocation
- catalogue provider invocation
- grade estimation

## 6. Individual-Photo Assessment Model

Phase 1 should classify assessment dimensions as follows.

Reliably deterministic now:

- file availability
- file accessibility
- zero-byte file
- supported extension
- image decode success
- image dimensions
- extremely small image
- image orientation from width/height
- brightness statistics
- underexposure heuristic
- overexposure heuristic
- contrast statistic
- blur/sharpness heuristic using Laplacian variance
- role metadata present or malformed
- duplicate path key

Approximate heuristic:

- excessive empty background
- subject coverage / framing
- glare or blown highlights
- consistency across a multi-photo set
- slab label presence by role metadata only
- date-area detail image by role metadata only
- variety-marker detail image by role metadata only

Requires future computer vision:

- reliable coin/banknote segmentation
- true subject coverage measurement
- visible obstruction detection
- perspective distortion correction
- glare localization on the collectible
- date-area visibility from pixels
- variety-marker visibility from pixels
- holder-label readability
- coin surface wear-point assessment
- surface-mark recognition

Out of scope:

- identification
- OCR text extraction
- variety attribution
- grade prediction
- submission-readiness advice
- automatic image correction
- deciding whether the item is a coin or unrelated photo

Recommended Level A individual checks:

- path exists
- supported format
- readable by OpenCV/Pillow
- width and height above thresholds
- brightness within thresholds
- contrast above threshold
- sharpness above threshold
- role is recognized

Do not claim that Level A sees the coin surface. It sees file and image-quality properties.

## 7. Photo-Set Aggregation Model

A photo set should be assessed at two levels:

1. Each individual photo.
2. The set as evidence for downstream tasks.

Aggregation inputs:

- ordered `ItemPhoto` records
- role metadata
- per-photo readiness scores
- per-photo blocking issues
- duplicate path keys
- configured expectation for certified items

Required roles by default:

- broad identification:
  - front or obverse recommended
  - back or reverse recommended

- OCR:
  - at least one readable front/back/detail photo
  - close-up detail improves readiness but should not be mandatory for all cases

- variety attribution:
  - front/back plus detail photo for date or marker

- grade estimation:
  - front and back required
  - both need high sharpness and usable exposure
  - no blocking image-quality issues

- submission-readiness:
  - front, back, and any certification label if certified
  - stronger evidence than grade estimation because recommendation depends on confidence and documentation

One bad photo should not crash or invalidate the entire report. The set report should surface partial readiness:

```text
Broad identification: MAYBE
OCR: MAYBE
Variety attribution: NO
Grade estimation: NO
Submission readiness: NO
```

## 8. Readiness Decisions By Downstream Task

Readiness must be first-class per downstream task because the same photos may be sufficient for one task and insufficient for another.

Recommended task gates:

- `BROAD_IDENTIFICATION`
  - Can proceed with a single readable side, but confidence should be limited.
  - Front and back increase readiness.

- `OCR`
  - Requires readable dimensions, contrast, brightness, and sharpness.
  - Missing close-up/date detail should produce `MAYBE`, not always `NO`.

- `VARIETY_ATTRIBUTION`
  - Requires sharper and more specific evidence.
  - Should usually be `NO` unless detail roles or strong image quality are present.

- `GRADE_ESTIMATION`
  - Should be conservative.
  - Requires front and back, good sharpness, usable exposure, and no major blocking file issues.
  - Phase 1 does not grade; it only says whether later grading is safe to attempt.

- `SUBMISSION_READINESS`
  - Should be stricter than grade estimation.
  - Requires the photo set needed to support identity, condition, and documentation.
  - Certified items should include holder or certification-label evidence.

Recommended decision vocabulary:

```text
READY
MAYBE
NOT_READY
```

These map cleanly to the product language:

- ready to attempt
- limited; use cautiously
- do not attempt yet

## 9. Deterministic Scoring Model

Recommend a deterministic 0-100 readiness score for each photo and set.

The score is not objective photographic truth and not a probability of correct grading. It is a quality index derived from fixed checks.

Suggested individual photo score:

```text
Start: 100

Blocking floors:
- missing file: score 0, NOT_READY
- inaccessible file: score 0, NOT_READY
- unsupported extension: max score 20
- unreadable/corrupted image: score 0, NOT_READY
- zero-byte file: score 0, NOT_READY

Deterministic deductions:
- width or height below 300 px: -35
- width or height below 800 px: -15
- very low sharpness: -30
- moderate blur: -15
- low contrast: -15
- very dark image: -20
- very bright image: -20
- likely blown highlights: -15
- malformed role metadata: -5

Caps:
- missing role: max score 85
- unsupported but existing file: max score 20
- any blocking issue: max score 40 unless the issue is fatal
```

Suggested set score:

```text
Base: weighted average of valid individual photo scores

Set-level deductions:
- no photos: score 0
- only one side present: -25
- missing reverse/back: -20
- missing front/obverse: -20
- duplicate references: -5 each, cap -15
- certified expected but no holder/label photo: -20
- no detail photo for variety-sensitive workflow: cap variety permission at NO

Set-level caps:
- no front/back pair: max grade-estimation permission MAYBE
- only one valid image: max overall decision MAYBE
- all images blocked: score 0, NOT_READY
```

Suggested decision thresholds:

```text
READY: 80-100 and no blocking issues for the requested task
MAYBE: 50-79 or non-blocking limitations
NOT_READY: 0-49 or blocking task issue
```

Suggested confidence:

```text
HIGH:
- required checks completed
- no unreadable inputs
- deterministic metrics available

MEDIUM:
- some metrics available
- one or more non-blocking limitations

LOW:
- missing files
- unreadable files
- insufficient role metadata
- set-level evidence incomplete
```

All weights and thresholds should be constants in the engine, not magic values embedded throughout workflows.

## 10. Evidence And Explainability Rules

Every report should include human-readable evidence.

Rules:

- Evidence order must be deterministic.
- Strengths should explain what passed.
- Issues should explain what reduced the score.
- Blocking issues should explain what prevents downstream use.
- Recommended actions should directly correspond to issues.
- Numeric scores must be traceable to factors.
- Confidence must describe confidence in the readiness judgment, not confidence in identification or grading.

Example:

```text
Strengths
- front photo is present
- back photo is present
- primary photo is readable
- contrast is acceptable

Problems
- reverse photo is moderately blurred
- no certification label photo found

Recommended next photos
- retake reverse photo with sharper focus
- add certification label photo
```

No generated statement should imply:

- the coin is identified
- the coin is graded
- a variety is confirmed
- certification is recommended

## 11. Error And Degraded-State Handling

Required behavior:

- Missing files:
  - emit a per-photo fatal issue
  - continue assessing the rest of the set

- Broken OneDrive paths:
  - treat as missing or inaccessible
  - recommend waiting for sync or choosing a local file

- Partially synced files:
  - detect zero bytes or unreadable decode
  - recommend waiting for sync

- Unsupported formats:
  - mark as unsupported
  - do not attempt decode

- Zero-byte files:
  - mark as fatal

- Corrupted images:
  - mark as unreadable

- Extremely small images:
  - reduce score and block grading/submission tasks

- Duplicate image references:
  - report duplicates deterministically
  - do not mutate or dedupe the item

- One-sided photo sets:
  - allow limited broad identification
  - block grading and submission readiness

- Missing slab labels:
  - only relevant when certified item context is supplied
  - block submission readiness more than broad identification

- Malformed photo-role metadata:
  - normalize to `OTHER` using existing `PhotoRole` logic where possible
  - reduce confidence

- Inaccessible files:
  - record error and continue

- Mixed coin and unrelated photos:
  - Phase 1 cannot reliably detect this from pixels
  - flag only if role metadata or unsupported file evidence suggests a problem

No single bad image should crash assessment of the entire set.

## 16. Regression Risks

Risk: accidentally expanding old CV behavior.

- Mitigation: implement Level A only and do not call `CoinRecognizer.detect_coin()`.

Risk: implying grade or identification confidence.

- Mitigation: name outputs as readiness, permission, and quality metrics only.

Risk: mutating collection photo metadata during assessment.

- Mitigation: engine accepts copied inputs and returns DTOs only.

Risk: making existing OCR/grading workflows fail.

- Mitigation: do not wire gates into production workflows until a later approved phase.

Risk: flaky image tests.

- Mitigation: use synthetic local images with deterministic dimensions and pixel values.

Risk: overfitting thresholds to one camera or one image set.

- Mitigation: conservative thresholds and explainability-first reporting.

Risk: OneDrive partially synced files.

- Mitigation: explicit missing/unreadable/zero-byte handling.

Risk: duplicated Photo Vault logic.

- Mitigation: Image Assessment measures readiness; Photo Vault audits metadata coverage.

## 19. Clear Recommendation

Recommendation:

```text
Implement Level A now.
Defer Level B.
Do not reject the phase.
```

Level A should include:

- file availability
- supported format
- image decode success
- dimensions
- brightness
- contrast
- sharpness / blur heuristic
- role completeness
- front/back set coverage
- deterministic downstream permissions
- explainable recommended next photos

Level B should be deferred:

- coin segmentation
- glare localization
- rotation correction
- subject coverage from pixels
- obstruction detection
- holder-label readability
- date/variety-marker detection
- surface-mark recognition
- wear-point analysis

Phase 1 is valuable because it gives every later intelligence layer a trustworthy gate:

```text
Do we have enough photo evidence to attempt this analysis?
```

That is a necessary foundation for Canadian Reference Intelligence and Grading Readiness.
