# v8.7 Phase 2 Design: Photo Inbox

Design status: proposed for review.

Implementation status: Phase 2A backend implemented. Phase 2B.1 read-only GUI implemented.

Phase baseline:

- Phase 1A added editable collection-entry suggestions.
- Phase 1B added `CoinItem.photos` as the structured photo metadata source of truth.
- Phase 1C added multi-photo entry and item-detail gallery support.
- Phase 2A added a backend-only `PhotoInboxManager`.
- Phase 2B.1 added a manual Photo Inbox window for refresh, review, defer, and ignore.
- `image_path` remains the compatibility alias for the primary photo.
- Photo Vault remains an indexing and audit layer, not a competing photo owner.
- The repository already contains `coin_photos/incoming`.

This document records the approved Phase 2 design and the Phase 2A backend boundary.

## 1. Root-Cause Analysis

The largest remaining photo friction now happens before Coin Analyzer receives the photos.

Current collector workflow:

```text
Coin
->
Take photos on iPhone
->
Email myself
->
Open laptop
->
Download attachments
->
Browse for files
->
Upload into Coin Analyzer
```

The root cause is not that the collection-entry form lacks another button. The root cause is that the collector has to act as a file-transfer and file-routing system before using the product.

The product opportunity is to remove the manual Browse step for photos that already arrived in a known local folder. Coin Analyzer should notice those photos, group likely related images, and offer clear next actions:

- Create New Collectible
- Attach to Existing Collectible
- Ignore
- Defer

This should remain local-first and cloud-optional. OneDrive, iCloud Drive, Dropbox, Google Drive, NAS folders, and plain local folders should all be treated as filesystem locations. Coin Analyzer should not depend on any specific provider.

## 2. Current Architecture Affected

Current photo-related architecture:

- `CoinItem.photos`
  - Item-owned structured photo metadata.
  - Source of truth once a photo is attached to a collection item.
- `ItemPhoto`
  - Path, role, primary flag, notes, and display order.
- `PhotoRole`
  - Shared role vocabulary for front, back, holder, edge, detail, certification label, and other.
- `image_path`
  - Backward-compatible primary-image alias.
- `PhotoVault`
  - Indexes and audits item-owned and supplemental photo metadata.
- `coin_collection_gui.py`
  - Main collection-entry form, item details, edit item flow, Photo Vault views, and older photo-assisted workflows.
- `coin_photos/`
  - Existing local photo directory with `incoming`, `collection`, `references`, `candidates`, `auction_wins`, `sold`, and `raw`.

Current gaps:

- No durable Photo Inbox state exists.
- No watched-folder service exists.
- No Photo Set grouping model exists.
- No queue of unprocessed incoming photos exists.
- Existing workflows still expect the collector to browse for files or choose a folder manually.

## 3. Recommended Ownership

Recommended ownership model:

- `PhotoInboxService`
  - Owns scanning, detecting stable files, grouping into Photo Sets, and updating inbox state.
- `PhotoInboxState`
  - Owns durable lifecycle state for inbox photos and Photo Sets.
- `PhotoSet`
  - Owns a proposed group of related photos before attachment to a collectible.
- `CoinItem.photos`
  - Owns photos after the collector chooses Create New Collectible or Attach to Existing Collectible.
- `PhotoVault`
  - Continues to audit and index photos after they are attached or otherwise registered. It should not decide inbox state.

The inbox should be a staging area. It should not become a second collection model.

## 4. Inbox Service Design

Proposed module:

- `photo_inbox.py`

Core responsibilities:

- Load Photo Inbox configuration.
- Scan the configured incoming folder.
- Detect new image files.
- Wait until files appear stable before processing.
- Create or update Photo Sets.
- Persist inbox lifecycle state.
- Mark files as imported, attached, ignored, deferred, or errored.
- Avoid reprocessing files already seen.

Suggested classes:

- `PhotoInboxConfig`
  - `inbox_folder`
  - `grouping_window_seconds`
  - `supported_extensions`
  - `file_stability_seconds`
  - `max_inbox_items`
  - `file_management_mode`
- `InboxPhoto`
  - `path`
  - `fingerprint`
  - `filename`
  - `created_at`
  - `modified_at`
  - `first_seen_at`
  - `last_seen_at`
  - `size_bytes`
  - `state`
  - `error`
- `PhotoSet`
  - `id`
  - `photo_ids`
  - `state`
  - `created_at`
  - `updated_at`
  - `suggested_label`
  - `notes`
- `PhotoInboxService`
  - `scan()`
  - `get_pending_sets()`
  - `defer_set(photo_set_id)`
  - `ignore_set(photo_set_id)`
  - `attach_set(photo_set_id, item_id, roles)`
  - `import_set_as_new_collectible(photo_set_id, draft_fields, roles)`
  - `merge_sets(source_ids)`
  - `split_set(photo_set_id, photo_ids)`

The service should be synchronous in Phase 2A. Background polling can be added later if needed, but a manual "Refresh Inbox" action is safer for the first implementation.

## 5. Photo Set Design

A Photo Set is a proposed group of related incoming images.

Initial grouping signals:

- Arrival timestamp
- File modification timestamp
- Filename similarity
- Same parent folder
- Configurable grouping window

Default grouping recommendation:

- Group image files discovered in the same folder within a short configurable window, such as 90 seconds.
- If filenames share a strong prefix, allow grouping across a slightly longer window.
- Never auto-attach a group to a collection item.
- Always allow manual merge and split before final action.

Tradeoffs:

- Creation timestamps are closer to when the photo was taken, but cloud sync can preserve, rewrite, or hide them inconsistently.
- Arrival timestamps are reliable inside Coin Analyzer, but they reflect sync timing rather than capture timing.
- Filename similarity works well for burst photos, but phone-generated filenames may not encode subject meaning.
- A grouping window is simple and explainable, but it can combine photos from two coins photographed quickly.
- Manual merge/split protects collector control but adds a small review step.

Recommended rule:

Use arrival time as the primary grouping signal, modification time as supporting evidence, and filename similarity as a confidence boost. Treat grouping as a proposal, not a fact.

Suggested Photo Set states:

- `NEW`
- `PROCESSING`
- `DEFERRED`
- `ATTACHED`
- `IMPORTED`
- `IGNORED`
- `ERROR`

Suggested photo-level states:

- `NEW`
- `STABILIZING`
- `READY`
- `ASSIGNED`
- `IGNORED`
- `ERROR`
- `MISSING`

Set state should live in the Photo Inbox state file, not in `CoinItem`.

## 6. Folder Monitoring Strategy

Phase 2 should start with explicit scans, not a daemon.

Recommended Phase 2A behavior:

- User opens Photo Inbox.
- User clicks Refresh, or the window refreshes on open.
- Service scans the configured folder.
- Stable new files appear as Photo Sets.

Reasons:

- Simple to test.
- Avoids locked-file and partially synced-file surprises.
- Avoids background polling while the app is closed.
- Keeps the first implementation local and predictable.

Possible later behavior:

- Optional polling while the GUI is open.
- Optional system file watcher if a dependency is approved.

Do not hard-code paths. The service should read the configured Photo Inbox Folder.

Supported folder sources:

- Local folder
- OneDrive folder
- iCloud Drive folder
- Dropbox folder
- Google Drive folder
- NAS-mounted folder

Coin Analyzer should treat all of these as normal filesystem paths.

## 8. Configuration Strategy

Add a configurable setting:

- Photo Inbox Folder

Default recommendation:

- `coin_photos/incoming`

Configuration should also allow:

- Grouping window in seconds
- File stability delay in seconds
- Supported file extensions
- File-management mode
- Inbox overflow warning threshold

Possible storage:

- Existing application preferences if a durable preference mechanism is already used.
- Otherwise, a small JSON config file such as `data/photo_inbox_config.json`.

Do not put machine-specific absolute paths into source-controlled defaults.

The collector should be able to change the folder from the GUI.

## 9. File-Management Strategy

This is the major product decision and should not be finalized without approval.

Option A: Reference files in place

Benefits:

- No file movement.
- Works with OneDrive, iCloud Drive, Dropbox, NAS, and local folders.
- Avoids accidental duplicate storage.
- Matches Phase 1B/1C rule that Coin Analyzer stores metadata and does not move image files automatically.
- Lowest implementation risk.

Costs:

- Collection portability depends on the original folder path.
- If the user cleans the inbox folder, references can break.
- Backups must include both collection JSON and external photo folders.

Option B: Move files into collection folders

Benefits:

- Clearer long-term organization.
- Easier to backup as one project photo tree.
- Inbox naturally empties after processing.
- Less risk of accidentally deleting attached photos from `incoming`.

Costs:

- Moving files from cloud folders can confuse sync expectations.
- File movement is higher risk and may feel invasive.
- The app must handle collisions, permissions, interrupted moves, and user trust.
- This conflicts with the current no automatic file move/copy/delete rule unless explicitly approved.

Option C: Offer both modes

Benefits:

- Collectors can choose their preferred organization.
- Local-first users can keep references in place.
- Project-managed users can import into `coin_photos/collection`.

Costs:

- More settings and support burden.
- More test cases.
- More explanations in the GUI.
- Higher chance of inconsistent behavior across users.

Recommendation:

Phase 2A should reference files in place only. It is the safest continuation of Phase 1B/1C and preserves collector trust.

Phase 2B can add an explicit "Import into collection photo folder" action only after product approval. That action should copy, not move, unless the collector explicitly chooses move. The default should remain non-destructive.

## 10. Error Handling

Duplicate photos:

- Use a fingerprint based on path, size, and modified timestamp in Phase 2A.
- Consider content hashing later if performance is acceptable.
- Show duplicates as already seen rather than silently reprocessing them.

Partially synced files:

- Require file size and modified timestamp to remain unchanged for a configurable stability delay.
- Mark as `STABILIZING` until stable.

Interrupted sync:

- Keep file in `STABILIZING` or `ERROR` with a clear message.
- Retry on refresh.

Unsupported formats:

- Ignore by default, or show as unsupported if they match common image-like extensions.
- Do not block the inbox.

Deleted files:

- Mark as `MISSING`.
- Keep state visible until user ignores or clears the record.

Renamed files:

- Treat as a new path unless fingerprinting can confidently match size and modified time.
- Do not mutate existing attached `CoinItem.photos` unless the collector confirms.

Missing files:

- Preserve metadata.
- Surface clear status in the inbox and Photo Vault audit.

Locked files:

- Treat as not stable.
- Retry on refresh.

Inbox overflow:

- Warn when pending files exceed a threshold.
- Offer filters by state.
- Do not auto-delete.

Accidental reprocessing:

- Persist seen file fingerprints.
- Mark ignored/imported/attached files as terminal unless the user reopens them.

## 11. Test Plan

Unit tests:

- Config defaults to `coin_photos/incoming`.
- Config supports custom inbox folder.
- New supported image files become `InboxPhoto` records.
- Unsupported files are ignored or marked unsupported.
- Partially synced files remain `STABILIZING`.
- Stable files become `READY`.
- Arrival-time grouping creates expected Photo Sets.
- Filename-similarity grouping boosts grouping.
- Grouping window separates unrelated sets.
- Manual merge combines Photo Sets.
- Manual split separates photos.
- Duplicate paths are not reprocessed.
- Deleted files become `MISSING`.
- Ignored sets remain ignored across reload.
- Deferred sets remain deferred across reload.
- Attach action emits `ItemPhoto` metadata without moving files.
- Import-as-new action creates a draft or collection item only through explicit user action.

Integration tests:

- Photo Inbox service loads and saves state idempotently.
- Legacy `CoinItem.photos` and `image_path` behavior remain unchanged.
- Photo Vault still indexes item-owned photos after attachment.
- Phase 1C multi-photo entry remains compatible with inbox-origin photos.
- CSV import/export behavior remains unchanged unless explicitly expanded.

GUI tests:

- Photo Inbox count displays pending sets.
- Refresh updates pending set count.
- Empty inbox shows a clear empty state.
- Missing files show warnings without blocking access.
- Create New Collectible passes photos to the existing collection-entry flow.
- Attach to Existing adds references without deleting files.
- Defer and Ignore update state only.

Regression gate:

```powershell
python -m unittest discover
```

## 13. Migration Impact

Recommended Phase 2A migration impact: none.

Reason:

- Inbox state is new and separate.
- Existing collection records remain readable.
- Existing `CoinItem.photos` remains source of truth after attachment.
- Existing `image_path` compatibility alias remains unchanged.
- Existing photo files are not moved.

Potential new state files:

- `data/photo_inbox_state.json`
- `data/photo_inbox_config.json`

Migration should not touch:

- `data/collection.json`
- existing photo files
- Photo Vault records

If a future phase adds managed importing into `coin_photos/collection`, that should be treated as a separate migration/file-management review.

## 14. Regression Risks

Primary risks:

- Accidentally treating the inbox as a second source of truth for collection photos.
- Reprocessing the same photos repeatedly.
- Grouping unrelated coins photographed close together.
- Missing photos that are still syncing.
- Moving or deleting user files without clear approval.
- Making Collector Home noisy with inbox alerts.
- Creating too much GUI surface before the service is proven.
- Breaking Phase 1C multi-photo entry assumptions.

Mitigations:

- Keep inbox state separate from `CoinItem`.
- Keep actions explicit.
- Start with manual refresh.
- Reference files in place for Phase 2A.
- Use clear states and retryable errors.
- Require tests for duplicates, missing files, stable-file detection, grouping, and state persistence.
- Keep Photo Vault as audit/index only.

Phase 2B - Photo Inbox GUI and explicit attach/import actions
Phase 2C - Optional managed import/copy workflow and advanced grouping controls

## Recommendation

Do not ship Photo Inbox as one undifferentiated phase.

Recommended path:

```text
Phase 2A - backend-only Photo Inbox service/state
Phase 2B - GUI review and attach/import actions
Phase 2C - optional managed file import, if approved
```

The file-management decision should remain a product decision. My recommendation is:

- Phase 2A: reference files in place only.
- Phase 2B: continue reference-in-place behavior for attach/import actions.
- Phase 2C: consider an explicit copy/import option after review.

Do not move, copy, rename, or delete source photo files by default.

Wait for approval before implementation.
