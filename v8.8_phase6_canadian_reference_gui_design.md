# v8.8 Phase 6 Design: Canadian References GUI Integration

Status: Design only
Implementation: Not started
Baseline: Phase 5 complete at `81dfcf7` with 1,499 tests passing

## Mission

Expose configured Canadian reference-provider data in the existing Collector Workspace as a read-only research surface.

The tab helps a collector research explicitly supplied reference data. It does not decide what a collection item is, infer an issue from collection data, or decide which source claim is correct.

```text
Configured providers or aggregator
-> CollectorWorkspace.get_canadian_references(...)
-> Canadian References workspace tab
-> existing Markdown export on the returned report
```

Product rule:

> Coin Analyzer presents source claims. The collector interprets them.

## Current State

Phase 4 provides:

- neutral Canadian reference DTOs, source attribution, and validation
- local JSON and manual reference providers
- exact normalized-`issue_id` aggregation only
- claim-level provenance, conflict DTOs, and provider-failure isolation

Phase 5 provides:

- `CollectorWorkspace.get_canadian_references(...)`
- mutually exclusive exact ID, search, and filter/list request modes
- `CanadianReferenceReport` with aggregate groups, claims, conflicts, validation, provider errors, and Markdown export
- session cache and `refresh()` behavior that preserves provider/aggregator instances
- a conditional Reports Panel descriptor when providers are configured

The existing Collector Workspace GUI already provides:

- a `ttk.Notebook` with dedicated read-only tabs
- a two-column, selectable-detail pattern in `Image Readiness`
- refresh through `CollectorWorkspace.refresh()`
- report-object Markdown export with a save dialog

The GUI currently does not configure, create, discover, or inject reference providers. Phase 6 must preserve that boundary. A future application-composition or settings phase may explicitly provide a local/manual provider or aggregator; that work is not part of this phase.

## 1. GUI Placement

Add a `Canadian References` tab to the existing Collector Workspace notebook, immediately after `Image Readiness` and before `Workflow`.

Rationale:

- It is a research surface, not an item-entry, Photo Vault, or collection-editing feature.
- It follows the existing workspace pattern without creating another window.
- It is visible alongside other read-only workspace reports while remaining separate from image readiness.
- It avoids implying that a selected collection item has been identified.

The tab should always be present in the workspace. When no provider configuration was injected, it shows a clear empty/configuration state instead of hiding the feature or attempting provider discovery.

### Provider Composition Boundary

`open_collector_workspace(...)` may pass a pre-existing, application-owned reference configuration into `CollectorWorkspace`:

- one injected `reference_provider_aggregator`, or
- one explicit `reference_providers` list, or
- neither.

Use a narrow GUI helper to select exactly one of those already-owned inputs. It must not instantiate `LocalJsonReferenceProvider`, `ManualReferenceProvider`, or `ReferenceProviderAggregator`; inspect local paths; load JSON; or persist configuration. If neither input exists, construct the workspace without reference configuration and render the valid no-provider state.

This keeps provider ownership outside the GUI and preserves Phase 5's mutually exclusive constructor rule.

## 2. Query Controls

Place a compact controls area at the top of the tab.

### Request Modes

Use a small mode selector implemented with existing `ttk` controls:

1. `Exact Issue ID`
2. `Search`
3. `Filter / List`

Only one mode is active at a time. The GUI constructs exactly one request for the active mode and calls only:

```python
workspace.get_canadian_references(...)
```

It must never call a provider or aggregator directly.

### Exact Issue ID

Show one editable `Issue ID` entry and a `Look Up` command. The supplied value is passed only as `issue_id`. It is not split into country, year, denomination, or any inferred fields.

### Search

Show the approved `ReferenceQuery` fields:

- text
- country
- denomination
- year
- authority
- mintmark
- variety

The query form builds a `ReferenceQuery` DTO from values the collector explicitly entered, then passes it as `query`. Constructing this request DTO is the GUI's only direct use of the neutral Phase 4 input contracts; it must not inspect provider data or apply matching/ranking logic.

### Filter / List

Show the approved `ReferenceFilters` fields:

- country
- denomination
- year
- authority
- monarch
- series

The filter form builds a `ReferenceFilters` DTO and passes it as `filters`.

### Submission and State

- Start with `Exact Issue ID` selected and an empty entry.
- Do not run a query on tab creation, on mode changes, from a selected collection row, or from a collection form value.
- An empty active-mode submission produces the workspace's structured degraded report, displayed as a request prompt. It must not trigger a broad list operation.
- Mode-local draft values may remain visible when the collector switches modes, but only the active mode is submitted. The UI does not merge values between modes.
- `Run` is enabled whenever a mode is active; it reports an empty request through the normal read-only report state rather than raising a GUI error.

No control label or result wording may say "match," "your coin," "identified," "likely," or "correct source."

## 3. Results Layout

Reuse the compact layout established by `Image Readiness`:

```text
Canadian References
-------------------------------------------------
[ Exact Issue ID | Search | Filter / List ] [Run] [Refresh] [Export Markdown]
[ active-mode fields ]

Request: exact issue ID | Providers: 2 | Groups: 1 | Claims: 12 | Conflicts: 1

Issue Groups and Records              Reference Details
------------------------              -----------------
[tree of issue groups]                [Records | Claims | Conflicts | Diagnostics]
  issue-key                            selected group or record detail
    source record
```

Use a horizontally split body with stable panes:

- **Left:** a `ttk.Treeview` of exact-ID issue groups, with source records as children. A group label contains the normalized issue key and factual counts only. A record child includes source name and source-record ID.
- **Right:** a compact `ttk.Notebook` or equivalent tabbed detail region containing `Records`, `Claims`, `Conflicts`, and `Diagnostics`. Each detail view is read-only text or a non-editable tree/table.

On first successful query, select the first returned issue group deterministically. When there are no groups, clear the selection and render the relevant empty/degraded content in the detail area.

Record detail presents fields as supplied by each record, including country, denomination, year/date text, authority, mintmark, variety, physical attributes, catalogue identifiers, and record warnings where present. It does not merge source records into a canonical issue.

## 4. Claim and Provenance Presentation

The `Claims` detail view lists claims in report order and includes:

- field name
- raw value
- normalized value
- provider ID
- source name and source ID
- source-record ID
- optional field-level `SourceRef` details and notes

The `Records` view shows source metadata needed to interpret the claim:

- source type
- edition
- attribution
- licence text, if supplied
- source URL, if supplied
- retrieval date and source notes, if supplied

Use neutral labels such as `Raw value`, `Normalized value`, `Source`, and `Source record`. Do not visually elevate a manual provider, colour-code a preferred source, hide any claim, or display a source as authoritative merely because it appears first.

## 5. Conflict Presentation

The `Conflicts` detail view displays conflicts grouped by:

- issue key
- field name
- conflict type

For every conflict, show every competing claim side by side or in a stable table with its raw value, normalized value, provider, source, and source-record ID. Show conflict notes when present.

Use the factual heading `Source disagreements`. Do not provide a `Resolve`, `Prefer`, `Accept`, `Override`, or `Use this value` control. No source priority, confidence-derived winner, or manual-record precedence may enter the GUI.

When no conflicts exist, show `No source disagreements reported for this request.`

## 6. Error, Empty, and Degraded States

All states render inside the tab. Never show a stack trace, and do not convert provider errors into a generic failure that hides healthy results.

| State | Required presentation |
| --- | --- |
| No request yet | `Enter an exact issue ID, search terms, or filters to research configured reference data.` |
| Empty active request | Show the workspace request error and leave the results empty. |
| No providers configured | `No Canadian reference providers are configured for this workspace.` Explain that this tab does not discover or import sources. |
| No results | `No source claims were returned for this request.` |
| Provider failure with healthy results | Show healthy groups normally; list each provider error under `Diagnostics`. |
| Validation findings | Show severity, code, provider/source identity where supplied, and message under `Diagnostics`. |
| Unexpected workspace degradation | Show the concise `engine_errors` text from the report; preserve the tab controls and allow retry. |

Warnings, provider errors, and validation findings are distinct categories. Do not label a provider error as a conflict or silently remove a failed provider from diagnostics.

## 7. Refresh and Export Behavior

### Refresh

The tab-level `Refresh` command follows the established Image Readiness lifecycle:

1. Call `workspace.refresh()`.
2. Re-submit the current explicit active-mode request through `get_canadian_references(...)`.
3. Re-render the returned report and preserve the selected issue-group key when it remains present; otherwise select the first group deterministically.

The workspace-wide `Refresh Workspace` button must also refresh the Canadian References tab. It must re-run only the current explicit request, if one exists. With no request, it displays the normal no-request state and must not list all provider records.

Refresh must not recreate an aggregator, mutate a provider, reload source configuration, or touch collection data.

### Markdown Export

`Export Markdown` exports only the currently displayed `CanadianReferenceReport` through its existing `report.export_markdown(path)` method. This mirrors the Image Readiness tab's current-report export pattern and avoids the generic Reports Panel's no-selection descriptor call.

- Disable the command, or show a concise warning, until a report exists.
- Use the existing save-file dialog and success/failure messages.
- Do not add CSV, a second export API, source-file export, or provider-data export.
- The existing Reports tab remains unchanged. Its conditional descriptor remains useful for metadata and generic no-selection reports, but it is not the export route for an active GUI query.

## 8. Test Plan

Add a focused headless GUI test module using a fake workspace and synthetic `CanadianReferenceReport` DTOs. Tests must assert calls to the workspace public API only; they must not use a real provider or aggregator from the GUI test.

Required coverage:

- Canadian References tab is registered in the Collector Workspace notebook.
- The tab renders a no-request state without querying providers.
- Exact ID mode calls `get_canadian_references(issue_id=...)` only.
- Search mode constructs and passes only an explicit `ReferenceQuery`.
- Filter/list mode constructs and passes only an explicit `ReferenceFilters`.
- Switching modes does not submit or merge inactive-mode values.
- No collection item, photo, OCR text, or selected collection row is used to derive a request.
- A populated report renders deterministic group and source-record labels.
- Selecting a group/record updates records, claims, conflicts, and diagnostics detail without mutation.
- Provenance shows raw and normalized values plus source/source-record identity.
- Conflicting claims show all sides and no winner/preferred-source wording.
- Provider errors and validation warnings remain visible alongside healthy groups.
- No-provider, empty-result, invalid request, and degraded-report states remain readable and stack-trace free.
- Tab refresh calls `workspace.refresh()` followed by the same explicit query.
- Workspace-wide refresh re-renders the active request without a broad provider scan.
- Markdown export calls the current report's existing `export_markdown(...)` method.
- Existing Image Readiness, Photo Vault, Reports Panel, and workspace refresh tests continue to pass.
- Full unittest discovery passes.

Use only synthetic, local, or user-owned test values. Do not add network tests, commercial catalogue fixtures, or web requests.

## 10. Regression Risks

| Risk | Mitigation |
| --- | --- |
| GUI creates or configures providers | Pass only pre-existing explicit provider inputs; show a no-provider state otherwise. |
| A collection item becomes an implicit lookup | Accept only collector-entered exact ID, search, or filter controls. |
| GUI bypasses the workspace | Call only `get_canadian_references(...)`; never call providers or aggregators directly. |
| Source claims look like a canonical fact | Preserve source record boundaries and label raw/normalized values explicitly. |
| Conflicts gain an implicit winner through layout | Show every competing claim in stable report order with no selection control. |
| Refresh performs an unintended broad list | Re-run only the current explicit request; no request means no query. |
| Generic Reports export loses the active query | Export the current report object using its existing Markdown method. |
| Large result sets make the dialog hard to scan | Keep factual summary counts, use a selectable tree, and encourage explicit filters rather than automatic full-provider browsing. |
| Existing workspace refresh breaks dedicated tabs | Extend `_refresh_workspace_tabs(...)` using the established Image Readiness pattern and retain existing panel behavior. |
| Unrelated artifacts enter the commit | Review `git status --short` and stage only Phase 6 source, test, and design files. |

## 11. Explicit Out of Scope

Phase 6 must not include:

- collection-derived queries or any collection-item matching
- fuzzy matching, candidate identification, ranking, or `this is your coin` language
- OCR, image analysis, variety attribution, grading, grading readiness, pricing, or market analysis
- provider creation, provider configuration UI, provider discovery, local path browsing, JSON import, or provider persistence
- manual-provider editing or provider mutation
- source precedence, conflict resolution, manual override precedence, or winner selection
- scraping, website automation, cloud APIs, external APIs, network calls, polling, watchers, or catalogue ingestion
- Charlton, Coins and Canada, Numista, commercial, licensed, proprietary, or other third-party catalogue content
- collection mutation, persistence redesign, file movement, or schema migration
- unrelated Collector Workspace redesign or new windows
- Phase 7 or any inference work

## Recommended Implementation Sequence

1. Add a narrow application-composition helper that passes only an already-owned reference provider list or aggregator into `CollectorWorkspace`, when present.
2. Add a `Canadian References` tab next to `Image Readiness` and record its tab state, including the current explicit request and current report.
3. Add mutually exclusive exact-ID, search, and filter/list controls that build the approved request DTOs without collection context.
4. Add result-tree, selection, detail, provenance, conflict, and diagnostics render helpers that operate only on `CanadianReferenceReport` data.
5. Add focused tab refresh and current-report Markdown export helpers.
6. Extend workspace-wide refresh to re-run only the active explicit request.
7. Add focused headless GUI tests using fake workspaces and synthetic reports.
8. Run the focused GUI test module.
9. Run `python -m unittest discover`.

Stop after the read-only research surface. Identification, provider configuration, catalogue ingestion, OCR, grading, pricing, and source-resolution workflows require separate design approval.
