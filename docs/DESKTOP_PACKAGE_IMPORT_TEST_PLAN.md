# Desktop Capture Package Import Test Plan

## Status

Design contract only. These tests describe required importer behavior; they do
not imply that the importer exists.

This plan verifies the behavior defined by the
[architecture contract](DESKTOP_PACKAGE_IMPORT_ARCHITECTURE.md) and the controls
defined by the [threat model](DESKTOP_PACKAGE_IMPORT_THREAT_MODEL.md).

## Purpose

Prove that format `1.0` capture packages can be previewed and imported without
trusting archive metadata, reading or mutating live collection data, creating
partial collection batches, losing image ownership, or changing existing
desktop workflows.

The test strategy follows the repository's standard-library `unittest` pattern.
All persistence paths, clocks, IDs, limits, and filesystem roots must be
injectable. Tests use temporary directories and never open or modify
`data/collection.json`.

## Normative Contract Vocabulary

Tests use the same terms and roots as the architecture and threat model:

```text
immutable package snapshot: data/imports/snapshots/
import lock:                 data/imports/package_import.lock
journal/audit record:        data/imports/journals/<import-id>.json
import-owned root:           coin_photos/collection/imports/<import-id>/
collection baseline:         exact-byte SHA-256 plus byte length, or
                             MISSING_COLLECTION_V1 plus zero
```

The durable phases are `PREPARED`, `COPYING_IMAGES`, `FILES_READY`,
`COMMITTING_COLLECTION`, `COLLECTION_COMMITTED`, `SUCCEEDED`, `ROLLING_BACK`,
`ROLLED_BACK`, `RECOVERY_REQUIRED`, `ROLLBACK_FAILED`, and `CANCELLED`.
Exclusive creation and no-overwrite behavior are mandatory. Cancellation before
collection commit compensates through `ROLLING_BACK`; cancellation is disabled
during the atomic collection replacement. Retry uses a fresh snapshot, baseline,
import ID, and duplicate analysis unless startup recovery is reconciling the
exact existing journal.

Every application collection writer uses the same import lock or a verified
already-held lease. Tests distinguish cooperating application writers from the
documented residual race with external tools that ignore the lock.

## Quality Gates

An implementation is not complete until:

1. focused unit and integration modules pass;
2. importer UI-helper tests pass headlessly;
3. all failure-injection and restart-recovery cases pass;
4. existing collection, photo, import, backup, and GUI tests pass unchanged;
5. the complete discovery suite passes without a reduced count;
6. `git diff --check` and the staged equivalent pass before an approved commit;
7. manual Tk acceptance confirms the interactions automation cannot verify.

No test may require network access, a mobile device, API credentials, or the
private mobile repository at runtime.

## Test Harness Requirements

### Deterministic builders

Provide test-only helpers for:

- manifest dictionaries with explicit timestamps and IDs;
- small JPEG and PNG images with known dimensions and hashes;
- ZIP archives with controlled entry metadata and ordering;
- duplicate archive names and path-collision cases;
- corrupt, truncated, and mismatched media;
- collection fixtures with injected storage paths;
- journal records at every durable phase;
- exclusive lock files with deterministic tokens, ownership metadata, verified
  ownership, contention, and uncertain stale ownership;
- managed-root, item-directory, and role-file collision fixtures;
- immutable package snapshots that can change before or after preview;
- snapshot owner records and advisory leases, including active, orphaned,
  corrupt, link-crossing, and journal-referenced snapshots;
- crash-phase simulation that persists on-disk state without running normal
  exception compensation;
- recovery re-entry fixtures that can be interrupted repeatedly.

### Snapshot and lock helpers

Required focused tests prove:

1. snapshot directories, owner records, lease files, and package files use
   exclusive creation and desktop-generated tokens;
2. active advisory-leased snapshots are skipped by startup cleanup;
3. proven unjournaled orphan snapshots are removed idempotently;
4. journal-referenced snapshots are delegated to import recovery;
5. corrupt or unprovable snapshot ownership returns
   `SNAPSHOT_RECOVERY_REQUIRED` without deletion;
   PID status alone never proves snapshot ownership;
6. every normal `CoinCollection.save_collection()` path contends on the same
   lock while an importer holds it;
7. a verified already-held lease avoids non-reentrant reacquisition during the
   batch save;
8. stale-lock recovery requires every documented proof and user confirmation;
9. PID status alone never permits stale-lock deletion;
10. proven stale-lock recovery uses an exclusive token-qualified quarantine
    rename before deletion.

The builder must allow deliberate contract violations without passing through
production writer validation.

### Injected dependencies

Tests must be able to inject:

- collection JSON path;
- managed image root;
- journal/audit root;
- snapshot root;
- import lock path and ownership verifier;
- package and entry limits;
- clock;
- import and desktop item ID factories;
- exclusive create, snapshot copy, lock, collection baseline, media copy, JSON
  replacement, audit write, and cleanup failures;
- synchronous executor for coordinator tests.

### Assertions shared by failure tests

Every pre-commit failure asserts:

- original collection bytes are unchanged;
- in-memory collection remains unchanged;
- no managed final references were added;
- no files outside the injected import root changed;
- scratch resources are removed or explicitly journalled for recovery;
- user-facing errors contain a category but no absolute source path.

Every successful import asserts:

- collection JSON parses as one complete document;
- all selected records are present exactly once;
- skipped records are absent;
- every persisted photo path exists under the managed root;
- persisted paths are desktop-generated and package-independent;
- the package can be deleted without breaking imported photos;
- the audit record is sanitized and internally consistent.

## Unit Tests: Archive Boundary

1. Accept a well-formed `.ca-package` ZIP.
2. Reject a valid ZIP with the wrong filename extension.
3. Reject non-ZIP bytes with the correct extension.
4. Reject encrypted entries.
5. Reject entry count above the configured limit.
6. Reject compressed package size above 256 MiB without reading the full body.
7. Reject total declared uncompressed size above the configured ceiling.
8. Reject a single image above the 40 MiB decoded-entry limit.
9. Reject suspicious compression ratio even when totals appear bounded.
10. Reject negative, inconsistent, or otherwise impossible ZIP size metadata.
11. Require exactly one root `capture_package.json`.
12. Reject missing manifest.
13. Reject duplicate manifest entries.
14. Reject a manifest nested under a directory.
15. Reject duplicate archive names.
16. Reject case-colliding names.
17. Reject Unicode-normalization-colliding names.
18. Reject `/absolute`, `../escape`, `a/../../escape`, and empty path segments.
19. Reject drive-letter, UNC-like, colon-containing, and backslash paths.
20. Reject NUL-containing names.
21. Reject Windows reserved device names and trailing dot/space collisions.
22. Reject symbolic links and non-regular special entries.
23. Accept ordinary directory entries only when they are required parents of
    referenced files; reject empty or unexpected directory trees.
24. Prove that validation never calls `extractall()`.
25. Prove that rejected archives create no persistent files.

## Unit Tests: Manifest Parsing

1. Parse the exact format `1.0` root object.
2. Require strict UTF-8.
3. Reject a byte-order mark under the strict UTF-8 v0.2 policy.
4. Reject malformed JSON.
5. Reject duplicate JSON object keys at every nesting level.
6. Require a root object, not array/scalar/null.
7. Require exact schema `coin-analyzer.capture-package`.
8. Reject unsupported package versions.
9. Require and validate `created_by`, `created_with`, and `exported_at`.
10. Require session ID/name and defined session timestamp fields.
11. Require `coins` to be an array within the configured count limit.
12. Require unique coin IDs.
13. Require unique, contiguous positions beginning at zero.
14. Reject bool values where integers are required.
15. Require positive bounded quantity.
16. Require country, denomination, and year strings within length limits.
17. Validate mint, seller, and notes string bounds.
18. Parse purchase price as finite non-negative `Decimal` from a string only.
19. Reject exponent notation if the package contract requires plain decimal text.
20. Validate three-letter purchase currency and uppercase normalization.
21. Validate real ISO calendar dates and nullable purchase date.
22. Validate composition enum exactly.
23. Require a real boolean for `is_bullion`.
24. Parse nullable ASW as finite non-negative decimal text.
25. Require front and reverse; permit optional edge.
26. Reject a fourth or unknown photo role under strict known-role validation.
27. Ignore bounded unknown additive fields without changing known behavior.
28. Reject excessive nesting, aggregate strings, or manifest bytes.

## Unit Tests: Media Validation

1. Accept matching JPEG bytes, `.jpg`, and `image/jpeg`.
2. Accept matching PNG bytes, `.png`, and `image/png`.
3. Reject `.jpeg` if format `1.0` permits only `.jpg`.
4. Reject extension/MIME mismatch.
5. Reject extension/magic-byte mismatch.
6. Reject declared byte-length mismatch.
7. Reject declared width or height mismatch.
8. Reject zero and negative dimensions.
9. Reject dimensions or pixel count above configured limits.
10. Reject corrupt, truncated, and undecodable media.
11. Reject polyglot or trailing-payload media.
12. Reject one archive entry reused by multiple roles or records.
13. Reject referenced entries that do not exist.
14. Reject every unreferenced non-directory entry.
15. Confirm SHA-256 is computed over exact validated bytes.
16. Confirm preview validation leaves no extracted file.
17. Convert media decoder warnings into categorized failures rather than process crashes.

## Unit Tests: Mapping and Preview

1. Build records in manifest position order.
2. Map country, denomination, year, notes, acquisition date, price, currency,
   seller/source, and quantity exactly as documented.
3. Preserve purchase-price precision as `Decimal`.
4. Derive `total_cost` and never import it.
5. Use one proposed `CoinItem` for a quantity greater than one.
6. Map front/reverse/edge to `FRONT`/`BACK`/`EDGE`.
7. Mark front primary deterministically.
8. Leave grade, Numista number, reference, and estimate blank/default.
9. Surface mint, composition, bullion, and ASW as unmapped audit facts.
10. Generate no desktop ID or directory during read-only preview if allocation is
    intentionally deferred; otherwise generate only ephemeral proposed IDs from
    an injected deterministic factory.
11. Do not include absolute package paths in preview DTOs intended for display or audit.
12. Prove preview does not call collection save, image copy, or journal methods.
13. Preserve the existing collection file byte-for-byte.
14. Produce deterministic warning and row ordering.

## Unit Tests: Duplicate Detection and Decisions

1. Same completed package SHA produces an exact replay warning.
2. Same package hash with a prior failed/rolled-back audit does not claim success.
3. Same producer/session/mobile ID plus both media hashes is high confidence.
4. Matching both managed media hashes identifies the expected desktop record.
5. Country/denomination/year alone remains a warning, not an automatic skip.
6. Seller, date, price, notes, and one image remain weak evidence.
7. Duplicate evidence order is deterministic.
8. Every proposed record receives exactly one decision.
9. Only `SKIP` and `IMPORT_AS_NEW` are accepted.
10. Missing, stale, or extra decisions block commit.
11. Exact replay defaults to Skip but can be explicitly changed to Import as new.
12. No service emits merge, replace, or overwrite actions.

## Unit Tests: Journal and Audit

1. Validate every required journal field and its type.
2. Require immutable import ID and package hash.
3. Persist generated desktop IDs and managed relative paths before copying.
4. Permit only the normative transitions among `PREPARED`, `COPYING_IMAGES`,
   `FILES_READY`, `COMMITTING_COLLECTION`, `COLLECTION_COMMITTED`, `SUCCEEDED`,
   `ROLLING_BACK`, `ROLLED_BACK`, `RECOVERY_REQUIRED`, `ROLLBACK_FAILED`, and
   `CANCELLED`.
5. Make repeated identical transition writes idempotent.
6. Reject same import ID with conflicting immutable identity.
7. Atomically replace the journal document.
8. Preserve the previous journal on serialization, write, flush, or replace failure.
9. Store basename, never absolute source path.
10. Store sanitized error category, never raw path-bearing exception text.
11. Produce deterministic terminal audit ordering.
12. Retain source coin-to-desktop ID mappings and counts.
13. Ensure successful audit paths are relative to the managed image root.
14. Retain the normative session and per-coin provenance fields.
15. Keep provenance-only fields out of unrelated `CoinItem` fields.
16. Omit snapshot paths and absolute source paths from terminal audit records.
17. Permit terminal rolled-back/cancelled compaction only after cleanup succeeds.
18. Never automatically remove recovery-required evidence.
19. Require `terminal_audit = null` in nonterminal phases and a complete
    validated DTO in successful/rolled-back/cancelled terminal records.
20. Reject audit-only fields added outside the required `terminal_audit` member.
21. Permit only documented same-phase progress updates and prove terminal audit
    identity is immutable; in `SUCCEEDED`, only clearing `cleanup_pending` and
    updating its timestamp are allowed.

## Integration Tests: Successful Import

1. Valid single-coin import.
2. Valid multi-coin import preserving order.
3. Mixed JPEG and PNG package.
4. Optional edge absent.
5. Quantity greater than one preserved in one record.
6. Blank optional purchase date and ASW.
7. Duplicate records skipped while selected new records import.
8. Explicit import-as-new despite a warning.
9. One atomic collection save for the complete batch.
10. Existing collection records remain byte-equivalent after reload apart from
    deterministic whole-document serialization effects already accepted by the
    existing saver.
11. Managed media survives deletion of the source package.
12. Successful journal becomes a terminal audit record.

## Integration Tests: Failure and Compensation

Inject failure at each mutable step:

1. import-lock acquisition;
2. initial `PREPARED` journal write;
3. import-root exclusive creation;
4. first media copy;
5. later media copy after earlier success;
6. copied-byte verification;
7. `FILES_READY` journal update;
8. prospective collection serialization;
9. `COMMITTING_COLLECTION` journal update;
10. temporary collection write;
11. collection `fsync`;
12. collection `os.replace`;
13. `COLLECTION_COMMITTED` or success-audit transition;
14. snapshot/scratch cleanup;
15. rollback directory removal;
16. rollback journal update;
17. import-lock release.

Verify the architecture's expected collection, image, journal, and retry state
for each point. A failure after collection commit must not delete valid records
or images merely because audit finalization failed.

## Integration Tests: Restart Recovery

Construct on-disk states rather than relying only on mocked exceptions:

1. `PREPARED` journal with no directory.
2. `COPYING_IMAGES` with a partial directory.
3. `FILES_READY` with a complete directory and no collection IDs.
4. `COMMITTING_COLLECTION` with no collection IDs.
5. `COMMITTING_COLLECTION` with all collection IDs and files.
6. `COLLECTION_COMMITTED` with all collection IDs and files.
7. Collection IDs present but one expected image missing.
8. `COLLECTION_COMMITTED` with leftover snapshot data.
9. Rolled-back record with leftover owned directory.
10. Malformed journal root.
11. One malformed record among valid terminal records.
12. Managed path escaping the configured root in a hostile journal.
13. Repeated interruption during recovery of each nonterminal phase.
14. Explicit recovery transitions out of `RECOVERY_REQUIRED` and
    `ROLLBACK_FAILED`, with every unlisted transition rejected.

Recovery deletes only verified import-owned paths. Ambiguous, corrupt, or
escaping paths produce `RECOVERY_REQUIRED`; failure to remove an otherwise
verified owned root produces `ROLLBACK_FAILED`. Both require deliberate
intervention.

## Manual Acceptance

Manual Windows/Tk testing is required after automation passes:

1. Open the supported `coin_collection_gui.py` application.
2. Discover the importer under File without documentation.
3. Cancel the file picker.
4. Select a deliberately invalid package and review the safe explanation.
5. Select a valid multi-coin package.
6. Inspect all photos, unmapped fields, and duplicate warnings.
7. Exercise keyboard-only navigation and window resizing.
8. Skip one record and import another as new.
9. Confirm the collection refreshes once and images remain available after the
   source package is moved or deleted.
10. Reopen the same package and confirm exact replay behavior.
11. Restart the application and confirm audit history/recovery status remains
    consistent.
12. Create and verify a backup after the import; document whether imported image
    bytes are or are not included.

Use synthetic data only. Do not use the collector's live package or live
`data/collection.json` for acceptance until a separately approved backup and
migration procedure exists.

## Exit Criteria

The importer may proceed to release review only when:

- every required automated layer passes;
- all failure points have deterministic outcomes;
- no test observes a partial collection batch;
- no successful record references a missing managed image;
- recovery never deletes unowned paths;
- exact replay is detected;
- only Skip and Import as new are possible;
- privacy assertions pass;
- the full existing suite remains green;
- manual Tk acceptance is recorded;
- documentation matches the implemented limits and backup behavior.

## Explicit Stop Line

This test plan does not authorize implementation, production fixture creation,
live collection access, mobile-repository modification, commits, pushes, tags,
or releases.
