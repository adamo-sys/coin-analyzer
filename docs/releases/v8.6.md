# v8.6 Release Notes - Collector Intelligence & Workflow

## Release Theme

v8.6 moves Coin Analyzer from isolated recommendations toward guided collector work.

The release goal is to make the application act more like a collection assistant: one workflow surface for reviewing acquisitions, collection issues, upgrades, duplicates, and daily inbox items, followed by dashboard, explainability, batch, health, and memory improvements.

## Mission

Collector Intelligence & Workflow turns existing engines into an organized assistant workflow while preserving the project's permanent rules: deterministic logic, local data, explainable recommendations, and explicit collector control.

### Phase 1 - Workflow Engine

Create a unified workflow entry point for:

- Acquisition Review
- Collection Review
- Upgrade Review
- Duplicate Review
- Daily Inbox

The workflow engine should route through existing modules instead of duplicating business logic. `collector_workflows.py` and `collector_workflow_integration.py` are the first places to inspect before implementing.

Expected shape:

- One public workflow engine/facade
- Stable workflow type enum or constants
- Shared workflow request DTO
- Shared workflow report DTO
- Deterministic routing to existing engines
- Workflow status, evidence, next actions, warnings, and source references
- Unit tests covering each workflow type

Non-goals:

- No collection mutation
- No automatic buying, selling, grading, deletion, or submission
- No new persistence layer in Phase 1
- No GUI changes in Phase 1 unless explicitly approved
- No replacement of existing engines

Status: complete. Phase 1 added unified workflow DTOs, workflow states, and `CollectorWorkflowEngine.run_workflow(request)` while preserving existing workflow APIs. Targeted workflow tests passed 18 OK; full regression passed 1272 OK.

### Phase 2 - Portfolio Dashboard

Promote portfolio and collection health metrics toward the application home surface.

Candidate metrics:

- Collection completion percentage
- Average grade
- Upgrade opportunities
- Collection value
- Silver weight
- Gold weight
- Wants completed
- Recent acquisitions
- ROI estimates from local data only

Phase 2 should reuse `portfolio_dashboard.py`, `portfolio_performance.py`, `collection_dashboard.py`, `melt_value_engine.py`, `market_awareness.py`, and workspace reports where possible.

### Phase 3 - Explainability Improvements

Every recommendation should answer why.

The target output pattern:

```text
BUY

Reasoning

- Newfoundland priority
- Better than owned VF20
- Population or availability signal supports attention
- Asking price below local market evidence
- Fits collection goals

Confidence: 93%
```

Phase 3 should standardize evidence, confidence, risk, and uncertainty language across workflow reports and recommendation displays.

### Phase 4 - Batch Processing

Improve folder-level photo processing into a productivity workflow:

```text
Folder of images
-> OCR
-> Identify
-> Match collection
-> Generate review report
```

Phase 4 should build on `batch_processing.py`, `photo_capture_workflow.py`, OCR modules, and collection matching logic. It remains review-only.

### Phase 5 - Collection Health

Create an annual-style collection checkup that identifies:

- Duplicates
- Lower-grade duplicates
- Upgrade candidates
- Missing key dates
- Overrepresented series
- Underrepresented series

Phase 5 should reuse Collection Intelligence, Collection Quality, Collection Integrity, Series Tracker, Portfolio Performance, and Advisor outputs.

### Phase 6 - Recommendation Memory

Add memory for prior decisions and observed opportunities:

- Coins passed on
- Coins bought
- Seller reliability
- Price history
- Repeated listings

The goal is to support comparisons such as:

> You passed on this coin two weeks ago at $120. It is now listed for $95.

Phase 6 needs an explicit persistence and privacy design before implementation. It should not quietly expand app state without a reviewed schema.

## Architectural Rules

1. Use existing engines first.
2. Keep workflows deterministic and testable.
3. Keep recommendation evidence source-labeled.
4. Preserve read-only review by default.
5. Avoid feature creep inside Phase 1.
6. Do not begin later phases until Phase 1 is complete and reviewed.
7. Any new persistence for recommendation memory requires explicit schema design.
8. GUI changes follow engine/API stabilization, not the other way around.
