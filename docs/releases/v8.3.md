## Overview

Collector Workspace is the unified operating system layer that brings every existing tool, engine, report, and workflow into a single, cohesive workspace. Instead of opening `Tools -> *` for every subsystem, the collector opens one window and sees everything that matters.

Collector Workspace does not add new intelligence, new grading logic, new collection storage, or new data models. It is a pure aggregation and orchestration layer that queries existing engines and presents their outputs in organized, actionable panels.

## Mission

Transform the application from a collection of standalone tools into a cohesive collector operating system. Every subsystem the collector has built—Photo Capture, Batch Processing, Collection Intelligence, AI Grading, Reports, Shopping, Workflow—should be accessible from one unified workspace.

## Design Principle

**Aggregator only. No data ownership. No intelligence duplication.**

The workspace owns no collection data. It owns no grade patterns. It owns no photos. It queries existing engines and displays their outputs. Existing engines remain the source of truth.

```
Collection (source of truth)
    ↓
Existing Engines (intelligence, analysis, reports)
    ↓
Collector Workspace (aggregation, presentation, orchestration)
    ↓
Panels (read-only display)
```

NOT:

```
Collection (source of truth)
    ↓
Collector Workspace (duplicate storage)
    ↓
Duplicate Collection (stale copy)
    ↓
Panels (possibly stale)
```

## Permanent Architectural Rule

**Workspace = ViewModel, not Business Logic.**

CollectorWorkspace contains **zero business logic**. It only requests, caches, and presents results from existing engines. The workspace never computes:

- Duplicate detection -> CollectionIntelligenceEngine
- Upgrade opportunities -> CollectionIntelligenceEngine
- Grade analysis -> AIGradingAssistant
- Want list logic -> WatchlistEngine + OpportunityEngine
- AI grading -> AIGradingAssistant
- Batch processing -> BatchProcessingEngine
- Collection summary -> CollectionDashboard
- Quality scoring -> CollectionQualityEngine
- Integrity audit -> CollectionIntegrityAudit

```
CollectionIntelligenceEngine
           |
AIGradingAssistant
           |
BatchProcessingEngine
           |
SmartShoppingAssistant
           |
CollectorWorkspace  <-  ViewModel only
           |
Panels  <-  read-only presentation
```

**The Workspace should aggregate results, not calculate them.**

    """Unified workspace — thin aggregation layer. No data ownership. No mutation."""

    def __init__(self, collection_items, ...):

        """Active workflows and today's tasks."""

## Guardrails

- **No duplicated intelligence:** Every analysis, score, recommendation, and report comes from an existing engine. The workspace does not recompute anything.
- **No duplicated collection:** The workspace does not copy, cache, or shadow collection data. It queries the source collection directly via existing engines.
- **No ML:** No machine learning, no neural networks, no AI models beyond the existing deterministic `AIGradingAssistant`.
- **No CV:** No computer vision, no image recognition, no image analysis.
- **Read-only aggregation:** The workspace queries and displays. All mutation flows through existing tools (e.g., "Open in Collection Assistant" launches the existing dialog).
- **Thin orchestration:** The workspace is a presentation layer. Existing engines remain the source of truth.
- **Refresh on demand:** Panels refresh by re-querying engines, not by reading stale cached data.
- **No new database:** No new storage format, no new JSON file, no new persistence layer.

## Architecture Summary

Collector Workspace Architecture

• Aggregator/ViewModel only — zero business logic
• 10 workspace panels (Dashboard, Inbox, Collection, Want List, Opportunities, AI Queue, Batch Queue, Photo Vault, Workflow, Data Safety)
• 16 report types with lazy generation and Markdown/CSV export
• Lazy engine initialization — engines created on first access, never recreated
• Lazy report generation — reports generated on demand, not eagerly
• In-memory cache only — no new persistence layer, no JSON files, no database
• Zero duplicated business logic — all computation delegated to existing engines
• Zero duplicated collection storage — workspace holds reference, not copy
• Read-only workspace — all mutation flows through existing tools
• Existing tools remain mutation entry points — "Open in Tool..." buttons only
• Error resilience — per-engine exception handling, inline warning display
• Refresh on demand — cache clear, engines preserved
• Lifecycle diagnostics — `get_lifecycle()` for engine state, cache status, health
