## 1. Fix `missing_photo_count` (Photo Vault → Workspace)

### Root cause

`PhotoVaultIntegrityAudit.run()` computes `missing_photo_references` by counting issues with `issue_type == "Missing Photo Reference"` (line 243). These issues are only created by `_record_issues()` when a photo record has a `file_path` but the file doesn't exist on disk. The `_collection_coverage_issues()` method creates "Collection Item Without Photo" issues for items without any linked photo record, but these are **not** counted as "Missing Photo Reference".

When no photo records exist at all:
- `_record_issues()` produces nothing → 0 missing references
- `_collection_coverage_issues()` produces "Collection Item Without Photo" issues for every item, but these aren't counted
- Result: `missing_photo_references = 0` despite 41 items lacking photos

The workspace's `get_photo_vault()` sets `report.missing_photo_count = audit_report.missing_photo_references` (line 812), inheriting this 0. The Advisor checks `missing_photo_count > 0`, so it produces no photo recommendation.

### Semantics

`missing_photo_count` should mean "collection items without photos" (coverage gap). The `missing_photo_references` from the audit means "photo records with broken file paths" (metadata integrity issue). These are different things.

### Proposed fix

In `collector_workspace.py:get_photo_vault()`:

```python
# BEFORE:
report.missing_photo_count = getattr(audit_report, "missing_photo_references", 0)

# AFTER:
report.missing_photo_count = getattr(audit_report, "missing_photo_references", 0)
# Also count collection items that have no photo record at all
if report.missing_photo_count == 0 and report.items_without_photos > 0:
    report.missing_photo_count = report.items_without_photos
```

This is a **workspace-level aggregation fix**, not an engine change. It correctly derives `missing_photo_count` from the coverage summary (which already counts items without photos) when the audit's broken-reference count is 0.

### Files affected
- `collector_workspace.py` — `get_photo_vault()` method only (1 line change)

### Public API impact
- `PhotoVaultReport.missing_photo_count` semantics: now correctly reflects items without photos in all cases, not just broken file paths. No DTO field changes.

### Test plan
- Add `test_photo_vault_missing_count_with_no_records` to `test_collector_workspace.py`: verify that when `photo_records=[]` and `collection_items=[...]`, `missing_photo_count > 0`.
- Existing `test_collector_advisor.py` test for photo vault should now produce recommendations with no photo records.

### Regression risk
- **Low.** The fix only activates when `missing_photo_references == 0` and `items_without_photos > 0`. Existing behavior with photo records is unchanged. The new value is what the Advisor already expected.

## 2. Connect workflow pending reviews → Inbox

### Root cause

`get_inbox()` (lines 559–607) only queries three sources:
1. `collection_assistant` → `collection_assistant_pending`
2. `batch_processing` → `batch_processing_pending` (hardcoded to 0)
3. `ai_grading` → `ai_grading_review` (hardcoded to 0)

`get_workflow_status()` (lines 822–845) queries `collector_workflows` and gets `pending_reviews`, but `get_inbox()` never calls it. Result: `workflow.pending_reviews: 6` but `inbox.total_pending: 0`.

### Proposed fix

In `collector_workspace.py:get_inbox()`:

```python
# Add after AIGrading query block (before total_pending calculation):

# Query CollectorWorkflowEngine for pending reviews
try:
    workflow = self._get_engine("collector_workflows")
    daily = workflow.daily_summary()
    summary = getattr(daily, "summary", None)
    if summary:
        workflow_pending = len(getattr(summary, "statuses", []))
        # Add to items list
        for status in getattr(summary, "statuses", [])[:10]:
            items.append({
                "source": "Workflow",
                "label": getattr(status, "name", "Pending Review"),
                "confidence": 0.0,
                "id": getattr(status, "id", ""),
            })
except Exception as e:
    errors.append(f"Workflows: {e}")
    workflow_pending = 0

# Update total_pending to include workflow
total_pending = (
    report.collection_assistant_pending 
    + report.batch_processing_pending 
    + report.ai_grading_review
    + workflow_pending
)
```

### Files affected
- `collector_workspace.py` — `get_inbox()` method

### Public API impact
- `InboxReport.total_pending` now includes workflow reviews. No DTO field changes.

### Test plan
- Add `test_inbox_includes_workflow_reviews` to `test_collector_workspace.py`: mock `collector_workflows` with pending statuses, verify `total_pending` > 0.

### Regression risk
- **Low.** The inbox already had a `total_pending` formula. Adding a term preserves existing behavior when workflow has no pending items. Graceful degradation: if workflow engine fails, `workflow_pending` defaults to 0.

## 3. Improve gap target quality (specific years)

### Root cause

`collection_intelligence.generate_gap_report_rows()` returns rows like:
```python
{
    "country": "Canada",
    "denomination": "50 cents",
    "missing_years": "1901, 1902, 1903, ...",
    "suggested_next_acquisitions": "Acquire missing date(s): 1901, 1902, 1903...",
    # ... no "year" field
}
```

The workspace's `get_want_list()` passes these rows directly to `report.gap_targets` (line 698). The Advisor then calls `gap.get("year", "")` which returns `""` (empty string), producing the title "Acquire Canada 50 cents" with no year.

### Proposed fix

In `collector_workspace.py:get_want_list()`, extract the first specific year from the gap row and add it to each target:

```python
# After: gaps = gap.get("series_rows", []) if isinstance(gap, dict) else []
# Before: report.gap_targets = [...]

gap_targets = []
for g in gaps:
    gap_dict = g.to_dict() if hasattr(g, "to_dict") else dict(g)
    # Extract first year from missing_years string
    missing_years = gap_dict.get("missing_years", "")
    if missing_years:
        # Parse first year from comma-separated list like "1901, 1902, 1903"
        first_year = missing_years.split(",")[0].strip()
        if first_year:
            gap_dict["year"] = first_year
    gap_targets.append(gap_dict)

report.gap_targets = gap_targets
```

This makes the recommendation actionable: "Acquire Canada 50 cents 1901" instead of "Acquire Canada 50 cents".

### Files affected
- `collector_workspace.py` — `get_want_list()` method

### Public API impact
- `WantListReport.gap_targets` items now include `"year"` field when available. No DTO field changes — the `gap_targets` is already `List[Dict[str, Any]]`.

### Test plan
- Add `test_want_list_gap_targets_include_year` to `test_collector_workspace.py`: create a collection with a gap, verify the first gap target has a non-empty `year`.
- Add to `test_collector_advisor.py`: verify that gap recommendations include a year in the title when the gap target provides one.

### Regression risk
- **Low.** If `missing_years` is empty or unparsable, `"year"` is not added and the Advisor falls back to its current behavior. No change to the engine.

## 4. Replace duplicate disposal threshold with actual duplicate count

### Root cause

`collector_advisor.recommend_duplicate_disposal()` (line 509):
```python
if summary.total_items > 50:
```

This is an arbitrary threshold. It ignores whether there are actual duplicates. A 41-item collection with 4 duplicate pairs gets no recommendation; a 51-item collection with 0 duplicates gets one.

The `collection_intelligence.detect_duplicates()` method already computes actual duplicate pairs. The workspace's `get_collection_summary()` doesn't expose this.

### Proposed fix

Two-part fix:

**Part A: Expose duplicate count in workspace.**

In `collector_workspace.py:get_collection_summary()`:

```python
# After the CollectionIntelligenceEngine query block:
try:
    intel_engine = self._get_engine("collection_intelligence")
    duplicates = intel_engine.detect_duplicates()
    report.duplicate_count = len(duplicates)
except Exception:
    report.duplicate_count = 0
```

Add `duplicate_count: int = 0` to `CollectionSummaryReport` DTO.

**Part B: Update Advisor to use actual duplicate count.**

In `collector_advisor.py:recommend_duplicate_disposal()`:

```python
# BEFORE:
if summary.total_items > 50:

# AFTER:
duplicate_count = getattr(summary, "duplicate_count", 0)
if duplicate_count > 0 or summary.total_items > 50:
    # Use actual duplicate count in evidence
```

Also update the evidence to reference actual duplicate count when available:
```python
if duplicate_count > 0:
    evidence.append(RecommendationReason(
        category="duplicate",
        description=f"{duplicate_count} duplicate pair(s) identified in collection",
        source_engine="collection_intelligence",
        confidence="HIGH",
    ))
```

### Files affected
- `collector_workspace.py` — `get_collection_summary()` (add duplicate count query)
- `collector_workspace.py` — `CollectionSummaryReport` DTO (add `duplicate_count: int = 0`)
- `collector_advisor.py` — `recommend_duplicate_disposal()` (use `duplicate_count`)

### Public API impact
- `CollectionSummaryReport` gains a new field `duplicate_count: int = 0`. This is a **minor DTO addition** with a default value — backward compatible for existing consumers that don't reference it.
- `CollectorAdvisor` behavior changes: now triggers duplicate disposal on actual duplicates, not just collection size.

### Test plan
- Add `test_collection_summary_duplicate_count` to `test_collector_workspace.py`: verify `duplicate_count` is populated when duplicates exist.
- Update `test_recommend_duplicate_disposal_small_collection` in `test_collector_advisor.py`: a collection with 10 items but 2 duplicates should now produce a recommendation.
- Add `test_recommend_duplicate_disposal_with_actual_duplicates` to `test_collector_advisor.py`: specifically test that duplicate pairs trigger the recommendation.

### Regression risk
- **Low-Medium.** Adding a DTO field is backward compatible. The Advisor change broadens when recommendations are triggered (more cases, not fewer), so existing users may see more recommendations — which is the intended improvement. The `> 50` fallback remains for cases where duplicate detection is unavailable.

## 5. Intrinsic opportunities from gaps

### Root cause

`get_opportunities()` (lines 717–763) calls `smart_shopping.generate_report()` first. When `self._shopping_candidates` is empty/None, this fails (caught on line 749–750). It then calls `opportunity_engine.generate_report()` but **only uses `budget_recommendations`** (line 756–757). The `OpportunityEngine.generate_report()` already calls `_collection_target_opportunities()` which generates want-list-based opportunities, but the workspace ignores them.

```python
# The workspace only uses budget_recommendations:
opp_report = opp.generate_report(self._shopping_candidates, limit=5)
budget = getattr(opp_report, "budget_recommendations", [])
report.budget_recommendations = budget if isinstance(budget, list) else []
# top_recommendations, total_opportunities, best_next_purchase remain empty!
```

### Proposed fix

In `collector_workspace.py:get_opportunities()`:

```python
# After the SmartShopping block (which may have failed), add:

# Fallback: use OpportunityEngine's collection-target opportunities when shopping candidates are empty
try:
    opp = self._get_engine("opportunity_engine")
    opp_report = opp.generate_report(self._shopping_candidates, limit=5)
    
    # Budget recommendations (existing behavior)
    budget = getattr(opp_report, "budget_recommendations", [])
    report.budget_recommendations = budget if isinstance(budget, list) else []
    
    # Intrinsic opportunities: use collection-target opportunities as fallback
    if not report.top_recommendations:
        top = getattr(opp_report, "top_overall", [])
        if top:
            report.top_recommendations = [r.to_dict() if hasattr(r, "to_dict") else dict(r) for r in top]
            report.total_opportunities = len(top)
            if top:
                report.best_next_purchase = getattr(top[0], "item_name", None)
except Exception as e:
    errors.append(f"Opportunity Engine: {e}")
```

This preserves existing behavior when shopping candidates are available, and fills the gap with intrinsic opportunities (want-list gaps) when they are not.

### Files affected
- `collector_workspace.py` — `get_opportunities()` method

### Public API impact
- `OpportunitiesReport.top_recommendations` and `total_opportunities` now populated when intrinsic opportunities exist. No DTO field changes.

### Test plan
- Add `test_opportunities_falls_back_to_intrinsic` to `test_collector_workspace.py`: create a workspace with no shopping candidates but with collection gaps, verify `top_recommendations` is populated from `OpportunityEngine`.
- Add `test_opportunities_prefers_shopping_when_available` to `test_collector_workspace.py`: verify that when shopping candidates exist, they take precedence.

### Regression risk
- **Low.** The fallback only activates when `smart_shopping` produces no results. Existing behavior with shopping candidates is preserved. The `OpportunityEngine` already generates these opportunities; the workspace was just ignoring them.

## Bonus finding: Grade normalization (not in approved scope)

During analysis, I discovered that `_grade_score()` in `collection_intelligence.py` uses `GRADE_HIERARCHY` with hyphenated keys (e.g., `"VG-8"`, `"F-12"`) but our test collection uses non-hyphenated grades (e.g., `"VG8"`, `"F12"`). This causes `_grade_score()` to return 0 for all items, which breaks `detect_upgrade_candidates()` (requires ≥2 items with grade_score > 0).

**Recommendation:** This should be addressed in a separate small fix, not Phase 4. The fix is to normalize grade strings before lookup (e.g., insert hyphen between letters and digits). It's a data quality issue, not directly related to the 5 approved signal fixes.
